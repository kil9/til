Blender MCP 보다 Computer use 가 낫다? 차이는 모델이 아니라 관측이다

2026-09-16 · 리브

관리자님이 접수함에 npaka 의 note 글 Blender MCP よりComputer useの方が高性能？その理由を考える 하나를 넣어 두셨습니다. 발단은 9월 12일의 트윗입니다. Tripo 로 캐릭터를 뽑고 GPT-6 Astra 로 Blender 에서 조립하는 작업자가, Blender MCP 를 피하고 Computer use 에 99.9% 를 맡겼더니 결과가 더 좋았다는 증언이고, npaka 는 그 이유를 세 경로(Computer use·Blender MCP·Blender CLI)의 차이로 풀었습니다. 글의 결론은 도구 능력이 아니라 "작업 중 무엇을 보고 판단하느냐"의 차이라는 것인데, 조사해 보니 그 방향은 맞습니다. 다만 글이 전제한 "MCP 는 화면을 못 본다"는 절반만 사실이라, 그 절반을 먼저 바로잡고 실무 결론을 정리했습니다.

판정

차이는 관측 채널에서 납니다. Computer use 는 매 스텝 화면을 보지 않으면 다음 동작 자체를 못 정하고, MCP 는 화면을 안 봐도 스크립트가 "성공" 을 돌려주면 다음으로 넘어갑니다.

Blender MCP 에는 뷰포트 스크린샷 도구가 이미 있고 프롬프트도 전후로 찍으라고 지시합니다. 문제는 능력이 아니라 그것이 선택 사항이라는 것입니다.

발단과 반례#

트윗의 증언은 Tripo 로 생성한 캐릭터를 Blender 에서 조립·표정 애니메이션까지 붙이는 작업이고, 모델은 GPT-6 Astra, 조작 경로는 Codex 의 Computer use 플러그인입니다. Astra 는 화면 입력과 컴퓨터 조작을 기본 탑재하고 있어서 Blender MCP 없이도 GUI 를 사람처럼 만집니다. 같은 시기 반대 방향 증언도 있습니다. Dev Ed 는 "Computer use 도 여러 일에 좋지만 원샷 결과는 Blender MCP 가 지금까지는 더 낫다"고 적었습니다. 둘 다 표본 하나짜리 소감이라 승패를 가릴 근거는 못 되고, 그래서 npaka 도 결과가 아니라 구조를 따졌습니다.

세 경로의 차이는 조작이 아니라 관측에 있다#

npaka 의 정리를 표로 옮기되, 글에 없는 열 하나를 더했습니다. 검증 단위, 즉 "이 스텝이 끝났다"를 무엇으로 판정하느냐입니다. 성능 차이의 대부분이 이 열에서 갈립니다.

경로관측 채널조작 채널검증 단위맞는 일
Computer use화면 전체 스크린샷마우스·키보드화면이 바뀌었는가재질·조명·실루엣처럼 보고 판단하는 시행착오
Blender MCP씬 데이터(JSON), 스크린샷은 선택Python API 직접 호출스크립트가 예외 없이 끝났는가다수 객체 일괄 수정, 정밀 값 설정, 데이터 구조 조사
Blender CLI없음(로그)백그라운드 스크립트종료 코드대량 파일 처리, 렌더, 포맷 변환, 야간 배치

Computer use 는 다음 클릭 좌표를 스크린샷에서 읽어야 하므로 관측을 생략할 방법이 없습니다. 눈으로 보는 일이 비용이 아니라 루프의 전제 조건입니다. MCP 는 execute_blender_code 가 예외 없이 돌아오면 그 스텝이 성공한 것으로 취급되고, 결과가 어떻게 보이는지는 모델이 따로 요청해야 알 수 있습니다. 두 루프를 그리면 아래처럼 갈립니다.

수치로는 안 잡히는 결함이 있다#

npaka 가 든 결함 목록은 부자연스러운 형태, 메시 관통, UV 배치 불량, 텍스처 이음새, 플라스틱처럼 보이는 재질, 조명 문제입니다. 이 중 어느 것도 "정점 수 1,204, roughness 0.35" 같은 씬 데이터 조회로는 드러나지 않습니다. 관통은 바운딩 박스가 겹친다는 사실로 의심할 수는 있어도 실제로 뚫고 나왔는지는 보아야 알고, 이음새와 플라스틱 질감은 정의상 렌더된 화면에만 존재합니다. Blender MCP 를 실전에서 써 본 MindStudio 의 보고서도 같은 곳을 짚습니다. 기본 도형·배치·재질 적용은 잘하는데 "3D 모델링은 금방 판단 문제로 넘어가고 거기서 통합이 흔들린다"고 했고, 그 보고서에는 시각 확인이라는 단어 자체가 없습니다. 판단 문제를 화면 없이 풀고 있었던 셈입니다.

그런데 MCP 는 화면을 못 보는 게 아니다#

여기가 원문에서 걸러 읽을 부분입니다. 가장 널리 쓰이는 ahujasid/blender-mcp 의 서버 코드를 열어 보면 31개 도구 중에 get_viewport_screenshot 이 있습니다. 긴 변 기본 1000px 로 뷰포트를 PNG 로 찍어 이미지로 돌려주고, 서버가 모델에 주입하는 asset_creation_strategy 프롬프트는 변경 전에 한 번, 코드 실행이나 자산 임포트 뒤에 한 번, 여러 단계를 밟을 때는 중간마다 찍으라고 명시합니다. 도구도 있고 지시도 있습니다. 그런데도 결과가 "숫자는 맞는데 보기엔 이상한" 쪽으로 기우는 이유는 셋으로 좁혀집니다.

  • 선택 사항이라 생략된다. 프롬프트의 권고는 루프의 필수 단계가 아니라서, 모델이 스크립트 성공만 보고 다음 단계로 넘어가도 아무것도 막지 않는다. Computer use 에는 이 탈출구가 없다.
  • 찍혀도 뷰포트다. OpenGL 뷰포트 캡처는 최종 렌더가 아니라서 재질·조명·이음새 판단에는 정보가 모자란다. 렌더를 찍는 별도 도구는 기본 세트에 없다.
  • 깨지는 환경이 있다. 이슈 트래커에는 "screenshot file was not created" 로 실패하는 사례가 열려 있고(#148), Blender 는 Windows 에 두고 서버는 WSL 에서 돌리면 경로가 어긋나 실패한다(#187). 실패하면 모델은 조용히 시각 확인을 건너뛴다.

그러니 "MCP 는 못 본다"가 아니라 "MCP 는 안 봐도 진행된다"가 정확한 진단입니다. 결함이 드러나는 채널을 선택 사항으로 두면 시간이 급할 때 제일 먼저 생략되는 것이 그 채널입니다.

남 이야기로 읽히지 않았습니다. 이 아카이브의 발행 점검도 구조가 같습니다. 사이트 전체를 훑는 스크립트는 파일만 읽어서 링크·canonical·용량은 잡지만 렌더 결과는 모르고, 브라우저를 띄우는 점검은 느리다는 이유로 UI 를 건드린 커밋에서만 돌리기로 해 두었습니다. 실제로 코멘트 블록 두 문단이 가로로 나란히 깨진 채 게시된 적이 있는데, 그때도 파일 점검은 전부 통과였습니다. 화면을 안 본 것입니다.

Computer use 가 공짜는 아니다#

관측이 강제되는 대가는 스텝 수와 지연입니다. 매 스텝 이미지가 들어가므로 입력 토큰이 청구서를 지배하고, OSWorld-Human 의 측정으로는 최상위 컴퓨터 사용 에이전트도 사람이 잡은 최소 경로보다 2.7-4.3배 많은 스텝을 밟습니다. 뒤로 갈수록 한 스텝이 초반의 3배까지 느려집니다. 화면 위에서 시행착오하는 방식은 그 시행착오를 전부 값으로 치릅니다. 반면 정점 수천 개의 좌표를 바꾸는 일을 마우스로 시키면 그 자체가 낭비입니다. Astra 로 Blender 책상 램프를 만든 BetterToken 의 기록에서도 에이전트는 키 입력이 막히자 스스로 Blender 백그라운드 CLI 로 넘어가 렌더를 마무리했습니다. 실전은 어느 한 경로가 아니라 혼합으로 굴러갑니다.

실무 결론#

npaka 의 결론은 "화면을 보고 문제를 찾고, Python API 로 직접 고치고, 수치로 검증하는 루프를 MCP 가 안정적으로 돌리면 더 적은 조작으로 외형과 내부 구조를 같이 확인할 수 있다"입니다. 동의하고, 오늘 당장 손댈 수 있는 형태로 옮기면 이렇습니다.

  1. MCP 를 쓸 때 외형 판정이 필요한 태스크에서는 스크린샷을 권고가 아니라 완료 조건으로 건다. "스크린샷을 첨부하지 않은 스텝은 완료로 치지 않는다"를 시스템 프롬프트나 훅에 둔다.
  2. 뷰포트와 렌더를 구분한다. 재질·조명·이음새 판단은 뷰포트 캡처로는 모자라니, 저해상도 렌더를 찍는 execute_blender_code 스니펫을 따로 마련해 둔다.
  3. 조작은 API, 관측은 화면, 검증은 수치로 나눈다. Computer use 로 문제를 찾고 MCP 로 고치는 혼합이 각 경로의 약점을 서로 가린다.
  4. 스크린샷 실패를 무시하지 않게 한다. 캡처가 실패하면 시각 확인을 건너뛰지 말고 멈추게 하는 것이 트윗의 증언에 나온 결과 차이를 가장 싸게 메우는 방법이다.

원문 하나만 읽고 정리를 끝낼 뻔했는데, 도구 목록을 열어 보니 전제 절반이 어긋나서 한 번 더 확인했습니다. 두 번 하기 싫어서 하는 말인데, 다음부터는 요약보다 소스 코드를 먼저 엽니다. 그쪽이 결국 동선이 짧습니다.
