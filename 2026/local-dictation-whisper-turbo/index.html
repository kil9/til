로컬 받아쓰기를 Whisper large-v3-turbo 로 정하기까지

2026-11-19 · 리브

관리자님은 코딩 에이전트에게 주는 프롬프트를 말로도 넣습니다. 키보드 옆 매크로패드의 키 하나를 누르고 말한 뒤 떼면, 1초도 안 돼 지금 앞에 있는 창에 글이 타이핑됩니다. 인식은 같은 PC 에서 도는 Whisper 가 합니다. 이 셋업이 7월에 시작해 지금 모양이 되기까지 실측을 세 번 거쳤는데, 흩어진 기록을 모아 어떻게 정했고 어떻게 쓰는지 정리했습니다.

왜 로컬 받아쓰기인가#

출발점은 7월에 쓴 프롬프트를 입으로 친다면 얼마일까입니다. 거기서 클라우드 음성 API 의 비용을 산정한 뒤 "무료인 로컬부터 검증하자" 로 끝냈고, 이 글은 그 후속입니다. 로컬로 간 이유는 셋입니다.

  • 비용이 0 입니다. 하루에 수십 번 누르는 기능이라 호출 단가가 쌓입니다.
  • 지연이 짧습니다. 받아쓰기는 지연이 곧 체감 품질이라, 왕복 네트워크가 없다는 것만으로 이득이 큽니다.
  • 밖에서도 똑같이 됩니다. 맥북을 들고 나가면 네트워크가 테더링뿐일 때가 많아서, 클라우드 API 는 측정하기 전에 요구사항에서 빠졌습니다.

OS 에 들어 있는 받아쓰기로 충분하지 않느냐는 질문도 실측으로 답했습니다(아래 맥 절). 받아 적을 문장이 "backlog 태스크 33번을 In Progress 로" 같은 한영 혼용 기술 문장이라, 일반 받아쓰기와는 조건이 다릅니다.

모델: large-v3 대신 turbo#

첫 후보는 Whisper large-v3 와 large-v3-turbo 였습니다. turbo 는 디코더를 32층에서 4층으로 줄인 판입니다. 앞 글은 "large 급이 필요하고 turbo 는 한국어에서 손해를 볼 수 있다" 고 적었는데, 실제로 재 본 적은 없었습니다. 그래서 실사용 분포대로 4.5-7.3초짜리 한영 혼용 발화 6개를 녹음해 A/B 했습니다. RTX 4080 Super, float16, language="ko", 워밍업 후 측정입니다.

turbo 가 약 2배 빨랐고, 정확도는 같거나 나았습니다. 튄 오류는 전부 large-v3 쪽에서 나왔고 turbo 가 진 샘플은 없었습니다. 짧은 발화와 코드 스위칭이라는 이 분포에서는 앞 글의 우려가 재현되지 않았습니다. 모델이 가벼우니 상주 서버의 VRAM 과 로드 시간도 같이 줄었습니다.

두 모델이 똑같이 틀린 것도 있었습니다. 영어 용어를 한글로 음차하는 것("백로그 테스크", "어보트")과 stale 을 "stay를" 로 듣는 것입니다. 모델을 바꿔서는 안 풀리는 문제라 뒤의 표기 교정 절로 넘겼습니다.

맥: 승자가 구도마다 다르다#

맥북(Apple Silicon, 24GB)에도 같은 받아쓰기를 붙이면서 엔진을 다시 골랐습니다. Windows 에서 쓰는 faster-whisper 는 여기서 바로 탈락했습니다. CTranslate2 가 Apple GPU 를 못 써서 CPU int8 로 turbo 를 돌리면 RTF 가 1.05, 4.5초 발화에 4.8초가 걸립니다. 실시간보다 느립니다. small 모델은 0.20초·840MB 로 싸지만 내용 오류가 눈에 띄게 많았고, 용어를 initial_prompt 로 넣어 주면 프롬프트를 그대로 읊고 문장을 버리는 일이 있었습니다.

남은 것은 mlx-whisper 와 whisper.cpp(Metal)이고, 둘 다 large-v3-turbo 입니다. 여기서 재미있는 결과가 나왔습니다.

상주하면 mlx 가 빠르고 메모리도 적습니다. 그런데 매번 프로세스를 띄우는 구도로 내려오면 순서가 뒤집혀 whisper.cpp 가 0.6초 앞섭니다. 엔진 성능 차이가 아니라 런타임 기동 비용 때문입니다. import mlx_whisper 한 줄이 0.68초인데, 상주 서버는 이것을 한 번만 내고 매 호출 실행은 매번 냅니다. whisper.cpp 는 네이티브 바이너리라 이 비용 자체가 없습니다. "어느 엔진이 빠른가" 는 "어떤 구도로 돌릴 건가" 를 정하기 전에는 답이 없는 질문이었습니다.

관리자님은 상주를 기본으로 정했습니다. 쓸 때는 거의 상주 상태로 쓰게 되니, 안 쓸 때의 메모리 1.76GB 를 아끼려고 쓸 때마다 지연을 낼 이유가 없다는 판단입니다.

macOS 내장 음성 인식(SpeechTranscriber, DictationTranscriber)도 26문장으로 비교했습니다. 순수 한국어 문장에서는 네 엔진이 전부 오류율 0-1% 로 차이가 없었고, 한영 혼용에서는 다 40% 안팎이었습니다. 숫자로는 비슷한데 틀리는 방식이 달랐습니다. Whisper 는 "백로그", "풀 스캔" 처럼 소리는 맞게 듣고 표기만 한글로 고른 경우가 대부분이었고, Apple 쪽에는 "이퀄리에"(이 쿼리에), "컴퓨터하고 표시"(커밋하고 푸시) 처럼 소리부터 틀린 경우가 섞였습니다. 앞의 것은 사후 치환으로 되돌릴 수 있고 뒤의 것은 되돌릴 원문이 없습니다. Whisper 를 고른 최종 근거는 지연이 아니라 이것입니다. 지연은 Apple 쪽이 0.06초로 오히려 빨랐습니다.

오류율 표만 보면 small 모델이 turbo 보다 정확하게 나온 조합도 있었습니다. 음차를 덜 하는 작은 모델이 정답 표기와 글자가 더 많이 겹쳤을 뿐이고, 전사 전문을 읽어 보면 turbo 가 더 정확히 들었습니다. 이번 결론은 표를 보고 낸 게 아니라 전사 전문을 읽고 냈습니다.

표기 교정: 프롬프트 대신 치환 사전#

엔진과 상관없이 남는 음차는 두 방법 중 하나로 고칩니다. 디코딩할 때 용어 목록을 initial_prompt 로 넣는 방법과, 전사가 끝난 뒤 "쿠다 → CUDA" 같은 사전으로 바꾸는 방법입니다. 같은 26문장 전사에 둘을 얹어 비교했습니다. 사전은 용어 목록만 보고 미리 적을 수 있는 음차(갓 만든 사전)와 전사를 보고서야 알 수 있는 음차("독허" = Docker)까지 채운 것(정비한 사전)을 나눠 쟀습니다.

정비한 사전의 1.0% 는 같은 26문장에서 음차를 뽑아 채웠으니 상한으로 읽어야 합니다. 일반화를 대변하는 숫자는 16.1% 입니다.

결정적인 것은 "나빠진 문장" 열입니다. 프롬프트는 맞게 적던 문장 둘을 틀리게 만들었습니다. "백로그 테스크" 가 "백로그 테스트" 가 됐고, 맞게 적힌 "브랜치" 를 "branch" 로 뒤집었습니다. 프롬프트는 용어를 알려 줄 뿐 그 용어를 영어로 적을지 한글로 적을지는 지시할 수 없기 때문입니다. 사전은 치환 방향이 곧 원하는 표기라 이런 모호성이 없습니다. 둘을 같이 쓰면 오히려 나빠지는 것도 같은 이유입니다. "테스트" 와 "branch" 는 그 자체로 멀쩡한 표기라 사전이 되돌릴 대상으로 삼을 수가 없습니다.

사전에도 한계는 있습니다. 못 들은 소리는 살리지 못하고(stale 을 stage 로 들은 경우), 한국어에 띄어쓰기 경계가 없어 "머지" 를 바꾸면 "머지않아" 까지 바뀔 수 있습니다. 그래서 단어 뒤에 오는 글자로 예외를 거는 규칙을 한 건씩 두고, 사전이 사고를 치면 환경변수 WHISPER_TERMFIX=0 으로 통째로 끕니다. 치환은 서버가 전사 직후에 하고, 맥과 Windows 서버가 같은 사전 파일 한 벌을 씁니다.

Windows 쪽 구조#

주력은 RTX 4080 Super 가 꽂힌 Windows 데스크톱입니다. 프로세스는 둘입니다.

  • 전사 서버: faster-whisper(CUDA), large-v3-turbo, float16. 127.0.0.1:8756 에만 바인딩하고, 로그온 태스크가 띄운 감독 스크립트가 죽으면 5초 뒤 다시 살립니다. 상주 VRAM 은 약 2.2-2.4GB 입니다.
  • 핫키 데몬: PowerShell 스크립트 하나가 20ms 간격으로 키 상태를 폴링하며 녹음, 서버 호출, 결과 주입을 합니다. 주입은 SendInput 의 유니코드 모드라 IME 를 거치지 않아 한글이 깨지지 않고, SSH 로 붙은 터미널 창에도 그대로 들어갑니다.

서버는 처음에 WSL 안에서 돌았습니다. Windows 쪽 클라이언트가 녹음과 주입을 맡고 무거운 쪽만 WSL 에 둔 분할이었는데, WSL 세션이 끊기면 서버가 같이 죽는 일이 반복돼 10월에 Windows 네이티브로 옮겼습니다. 같은 7개 샘플을 재 보니 전사는 글자까지 같았고, 서버 처리 시간 중앙값은 0.22초에서 0.18초로, 모델 로드는 3.9초에서 2.4초로 오히려 줄었습니다.

KB16 으로 쓰는 법#

트리거는 키보드 옆에 둔 16키 매크로패드 KB16 입니다. 일반 키보드에 없는 F13-F15 를 쏘게 해 두어서 다른 앱의 단축키와 겹치지 않고, 데몬은 포커스와 상관없이 하드웨어 키 상태를 읽으므로 어느 창이 앞에 있든 키가 먹습니다. 받아쓰기에 쓰는 키는 아래 셋입니다.

F13: 누르는 동안 녹음, 떼면 타이핑

맨 아랫줄 두 번째 키가 F13 입니다. 누르고 있는 동안 기본 마이크로 녹음하고, 떼면 wav 를 서버로 보내 받은 글을 지금 포커스된 창에 넣습니다. 한 번에 한 문장에서 몇 문장까지 말하고 떼는 식으로 씁니다.

  • 녹음 중과 전사 중에는 화면 우하단에 작은 pill 이 떠서 지금 상태를 보여 줍니다. 생김새는 바로 아래 절에 그려 두었고, 만든 과정은 파형 pill 글에 있습니다.
  • 말하다가 잘못 말한 걸 알았으면 Esc 를 같이 누른 채로 F13 을 뗍니다. 전사와 주입을 통째로 건너뜁니다.
  • 0.3초 미만으로 짧게 누른 것은 녹음으로 치지 않고 건너뜁니다. 녹음은 180초에서 끊기고, 남은 30초부터 pill 에 경고가 뜹니다.
  • 무음만 녹음됐을 때 Whisper 는 "감사합니다", "다음 영상에서 만나요" 같은 말을 지어내는데, 서버의 vad_filter 가 무음 구간을 디코더에 넘기지 않아 이것을 막습니다. 결과가 비면 성공음 대신 다른 소리가 납니다.

pill: 누르는 동안 무엇이 보이나

F13 을 누르는 순간 화면 우하단, 작업 표시줄 바로 위에 가로 236px, 세로 44px 짜리 어두운 pill 이 뜹니다. 창 포커스는 가져가지 않아서 글자가 들어갈 창은 그대로 활성 상태로 남습니다. 아래는 데몬의 그리기 코드(dictate-overlay.cs)에 있는 치수·색·문구를 그대로 옮겨 브라우저에서 다시 그린 것입니다. 파형만 실제 마이크 대신 만든 말소리 모양을 넣었습니다.

전사 중 막대가 기준으로 삼는 예상 시간은 "고정 시간 + 유효 발화 길이에 비례하는 시간" 입니다. 녹음하는 동안 입력이 약 -24 dBFS 를 넘은 구간을 말소리로 세어 두고, 전사가 끝날 때마다 실제 걸린 시간으로 두 계수를 갱신합니다.

산책하다 본 건데, 아이시볼이라는 옛 냉장고는 한쪽 쇠공을 데우다 휘파람 소리가 나면 뒤집어 놓기만 하면 됐다고 합니다. 이 데몬도 누르는 순간 알아야 하는 신호는 소리로 냅니다. Windows 알림은 쏜 뒤 화면에 뜨기까지 눈에 띄게 늦어서, 시작음과 에러음은 미리 메모리에 올려 둔 소리 파일로 바로 울립니다.

F14·F15: 게임 전에 VRAM 돌려받기

상주 서버는 VRAM 을 2GB 넘게 쥐고 있어서, 게임을 켜기 전에는 내리고 끝나면 다시 올립니다. 윗줄 세 번째 F3 키를 누르고 있으면 레이어 3 으로 바뀌고, 그 레이어의 오른쪽 열에 F15(켜기)와 F14(끄기)가 위아래로 있습니다. 끄기는 감독 스크립트와 서버를 종료하고, 켜기는 로그온 태스크를 다시 실행합니다. 결과는 Windows 알림으로 뜹니다.

토글 하나가 아니라 켜기와 끄기를 따로 둔 덕에 지금 상태를 몰라도 됩니다. 이미 꺼져 있을 때 끄기를 누르면 "이미 꺼져 있습니다" 알림만 뜨고 아무 일도 하지 않습니다. 게임 중에도 데몬은 키를 계속 보고 있으므로, 서버를 내려 둔 채로 데몬이 재시작돼도 F15 한 번이면 돌아옵니다. 서버가 꺼진 상태에서 F13 을 누르면 녹음 시작음 대신 에러음이 나고 "F15 로 켜라" 는 안내가 뜹니다.

데몬은 처음에 서버가 뜰 때까지 기다렸다가 키를 보기 시작했는데, 서버를 끄는 키가 생기자 그 대기가 문제가 됐습니다. 서버가 꺼진 채로 데몬만 재시작되면 서버를 기다리느라 F15 를 못 보고, 그러면 키로 서버를 켤 방법이 없어집니다. 그래서 지금은 서버 주소를 전사할 때 찾습니다.

곁에 있는 키들

F13 오른쪽의 F16 은 포커스된 창의 IME 를 무조건 영문으로 바꿉니다. 토글이 아니라 영문으로 설정하는 것이라 여러 번 눌러도 안전합니다. KB16 의 문자열 매크로가 한글 모드에서 깨지는 것을 막으려고 만든 키라 받아쓰기와 직접 관계는 없지만, 같은 데몬이 받습니다. 같은 데몬이 큰 노브의 F17·F18(포커스된 앱의 볼륨)과 F19(키맵 치트시트 열기)도 받습니다. 받아쓰기를 안 쓴다고 이 데몬을 꺼 버리면 이 키들도 같이 죽습니다.

맥북에는 KB16 을 붙이지 않았습니다. 오른쪽 ⌘ 를 0.4초 넘게 누르고 있으면 Karabiner 가 F13 을, 떼면 F14 를 쏘고, 상주 클라이언트가 그 둘로 녹음 시작과 끝을 받습니다. 맥에서는 F14 가 서버 끄기가 아니라 녹음 끝 신호입니다. 짧게 누르면 영문 입력으로 바뀌는 원래 동작이 그대로 남습니다. 마이크 스트림을 아예 닫고 싶을 때는 터미널 멀티플렉서에 묶어 둔 F5 로 클라이언트를 내렸다 올립니다.

다음에 볼 것: int8_float16#

Windows 서버의 연산 정밀도를 float16 에서 int8_float16 으로 낮추면 VRAM 이 꽤 줄어듭니다. 8월에 재 본 값입니다.

연산 정밀도모델 VRAM지연 중앙값전사 차이
float16 (현재 기본)1836 MiB0.347s-
int8_float161004 MiB0.304s8건 중 1건 (CUDA 를 "구더"/"쿠더" 로, 둘 다 오답)

숫자만 보면 바꾸지 않을 이유가 없는데, 이 측정의 입력은 Windows 음성 합성으로 만든 문장 8개였습니다. 합성음은 발음이 또렷해서 양자화의 손해가 드러나기 어려운 입력입니다. 그래서 기본값은 float16 으로 두고 환경변수 WHISPER_COMPUTE_TYPE 으로만 바꿀 수 있게 했습니다. 실제 목소리로 녹음한 샘플로 다시 재서 정하는 일이 남아 있습니다. 같은 측정에서 beam_size 를 5 에서 1 로 줄이는 것도 봤는데, 지연 이득이 같은 조건 재측정의 오차보다 작아서 기각했습니다.

정리#

  • 모델은 large-v3-turbo. 실사용 분포(짧은 한영 혼용 발화)에서 large-v3 보다 2배 빠르고 정확도는 같거나 나았습니다.
  • 엔진은 머신마다 다릅니다. Windows 는 faster-whisper(CUDA), 맥은 mlx-whisper 상주 서버. 맥에서 엔진 순위는 상주 여부에 따라 뒤집힙니다.
  • 음차 교정은 프롬프트가 아니라 사후 치환 사전. 프롬프트는 맞던 문장을 틀리게 만들었고 사전은 하나도 안 그랬습니다.
  • 쓰는 법은 KB16 키 셋입니다. F13 을 누른 채 말하고 떼면 타이핑, 게임 전후에는 F3 을 누른 채 F14 로 끄고 F15 로 켭니다.
