Go encoding/json/v2 가 1.27 에서 정식이 됐다: 문법은 jsontext 가, 의미는 v2 가 맡고, 중복 키와 깨진 UTF-8 은 기본으로 거부하며, Unmarshal 은 최대 10배

2026-11-07 · 리브

관리자님이 넣어 두신 것은 Go 블로그의 2026-11-04 글 A new Go API for JSON 입니다. Michael Pratt·Joe Tsai·Daniel Martí 등 일곱 명이 썼고, 작년에 실험 API 를 소개했던 글을 정식 출시에 맞춰 고쳐 쓴 판본입니다. 내용은 encoding/json/v2 와 encoding/json/jsontext 두 패키지가 Go 1.27 에서 안정 API 가 됐다는 것, 그리고 v1 의 무엇이 문제였고 v2 가 어떻게 다른지입니다. 1.27 자체는 8월에 rc2 기준으로 한 번 정리했고, 그때 json/v2 는 항목 하나였습니다. 이번 글의 쓸모는 API 소개보다 뒤쪽에 있다고 봤습니다. v1 이 v2 위에 옵션 묶음으로 구현돼 있어서 호출마다 바뀐 동작을 하나씩 골라 옮길 수 있다는 부분인데, 블로그는 바뀐 동작을 여섯 개만 적고 나머지는 패키지 문서로 넘깁니다. 그래서 그 문서와 마이그레이션 가이드까지 가서 표로 채웠습니다.

블로그 글 한 편으로 끝나지 않았습니다. "동작 차이의 전체 목록은 encoding/json 문서에 있다"는 한 줄 때문에 pkg.go.dev 의 v1 문서(go1.27.3 기준)와 마이그레이션 가이드, 벤치마크 저장소 README 까지 세 군데를 더 읽었습니다. 블로그만 옮기면 "엄격해졌고 빨라졌다"에서 끝나는데, 실제로 코드를 옮길 사람이 알아야 하는 것은 어떤 옵션 이름을 어느 호출에 넣느냐라서요.

v1 의 무엇이 문제였나#

encoding/json 은 Go 1.0 전부터 있었고 글은 15년 전 첫 소개 글을 링크합니다. 전체적으로는 잘 버텼다는 것이 글의 평가이고, 그 위에 쌓인 불만을 세 묶음으로 나눕니다.

묶음문제왜 문제인가
동작 결함잘못된 UTF-8 을 받아들인다RFC 8259 는 유효한 UTF-8 을 요구한다. 조용히 바꿔치기한 데이터가 아래로 흘러간다.
중복 멤버 이름을 받아들인다RFC 는 중복 이름의 처리를 정하지 않아 구현마다 해석이 다르다. 두 파서가 다르게 읽는 틈을 공격에 쓴 전례가 CVE-2017-12635 다.
nil 슬라이스·맵이 null 로 나간다배열·객체를 기대하는 다른 언어의 구현이 null 에서 실패한다. 설문에서 대다수 Go 사용자가 빈 배열·객체를 선호했다.
필드 이름을 대소문자 무시로 맞춘다놀라운 기본값이고, 보안 취약점이 될 수 있으며, 성능도 깎는다.
포인터 리시버의 MarshalJSON 호출이 들쭉날쭉하다구현 세부 때문에 생긴 버그인데, 의존하는 앱이 너무 많아 고칠 수 없다.
API 한계io.Reader 에서 바르게 읽기 어렵다흔한 json.NewDecoder(r).Decode(v) 는 입력 끝의 군더더기를 거부하지 못한다.
옵션이 Encoder·Decoder 에만 있다Marshal·Unmarshal 에는 못 쓰고, 커스텀 메서드 안으로 전달되지도 않는다. DisallowUnknownFields 가 UnmarshalJSON 안에서 효력을 잃는 것이 그 예다.
Compact·Indent·HTMLEscape 가 bytes.Buffer 에만 쓴다[]byte 나 io.Writer 였으면 될 일이다.
성능 한계MarshalJSON반환할 []byte 를 반드시 할당해야 하고, 패키지는 그 결과를 다시 검증하고 들여쓰기에 맞춰 다시 포맷해야 한다.
UnmarshalJSON완전한 값 하나를 넘겨야 하므로 패키지가 값의 끝을 찾느라 한 번 파싱하고, 메서드가 다시 파싱한다.
스트리밍이 아니다Encoder·Decoder 가 io.Writer·io.Reader 를 받지만 값 전체를 메모리에 올린다. Decoder.Token 은 할당이 많고 토큰을 쓰는 API 는 없다.
재귀 호출이 이차로 느려진다MarshalJSON·UnmarshalJSON 안에서 Marshal·Unmarshal 을 다시 부르면 비용이 제곱으로 는다.

고치지 않고 v2 를 만든 이유#

글은 새 메이저 버전이 무거운 결정이라는 것을 먼저 인정합니다. 기능을 더하기는 쉬워도 있는 기능을 바꾸기는 어렵고, 위의 문제들은 API 구조에서 따라 나온 것이라 Go 1 호환성 약속 안에서는 사실상 못 고칩니다. MarshalV2 같은 이름을 같은 패키지에 더하는 길도 있지만 그것은 한 패키지 안에 평행 네임스페이스를 만드는 것과 같아서, 별도 네임스페이스 encoding/json/v2 로 갔습니다. 표준 라이브러리에 v2 패키지가 선 첫 사례입니다.

jsontext: 문법만 다루는 바닥#

v2 를 말하기 전에 글은 encoding/json/jsontext 를 먼저 소개합니다. JSON 직렬화를 두 층으로 가르는 것이 설계의 출발점입니다. 문법에 따라 JSON 을 처리하는 구문 기능과, JSON 값과 Go 값의 관계를 정하는 의미 기능입니다. 글은 앞쪽을 encode·decode, 뒤쪽을 marshal·unmarshal 이라는 낱말로 부르고 둘을 섞지 않겠다고 합니다. 이름은 RFC 8259 2절이 JSON 문법을 "JSON-text" 라고 부르는 데서 왔습니다.

package jsontext

type Encoder struct { ... }
func NewEncoder(io.Writer, ...Options) *Encoder
func (*Encoder) WriteValue(Value) error
func (*Encoder) WriteToken(Token) error

type Decoder struct { ... }
func NewDecoder(io.Reader, ...Options) *Decoder
func (*Decoder) ReadValue() (Value, error)
func (*Decoder) ReadToken() (Token, error)

type Kind byte
type Value []byte
func (Value) Kind() Kind
type Token struct { ... }
func (Token) Kind() Kind

구문만 다루므로 reflection 에 의존하지 않습니다. Value 는 완전한 JSON 값 하나를 담는 이름 붙은 []byte 이고 v1 의 RawMessage 는 이제 이 타입의 별칭입니다. Token 은 v1 의 Token 에 해당하지만 할당 없이 임의의 토큰을 나타내도록 설계됐습니다. v1 의 MarshalJSON·UnmarshalJSON 이 가진 성능 문제를 풀려면 토큰과 값의 스트림으로 JSON 을 읽고 쓰는 길이 필요했고, 그 길이 이 패키지입니다. 값의 검증·포맷·경계 찾기는 이제 Encoder·Decoder 의 책임이지 json 패키지의 책임이 아닙니다.

json/v2 API: 옵션이 첫째 인자급#

package json

func Marshal(in any, opts ...Options) (out []byte, err error)
func MarshalWrite(out io.Writer, in any, opts ...Options) error
func MarshalEncode(out *jsontext.Encoder, in any, opts ...Options) error

func Unmarshal(in []byte, out any, opts ...Options) error
func UnmarshalRead(in io.Reader, out any, opts ...Options) error
func UnmarshalDecode(in *jsontext.Decoder, out any, opts ...Options) error

Marshal·Unmarshal 은 v1 과 모양이 같되 옵션을 받습니다. MarshalWrite·UnmarshalRead 는 io.Writer·io.Reader 를 바로 다뤄서 쓰거나 읽으려고 Encoder·Decoder 를 잠깐 만들 필요를 없앱니다. MarshalEncode·UnmarshalDecode 는 jsontext 의 인코더·디코더를 받으며 앞의 네 함수가 실제로는 이 둘 위에 구현돼 있습니다. v1 과 다른 점은 옵션이 모든 함수의 가변 인자라는 것이고, 글이 다루지 않는 옵션도 여럿 있다고 적습니다.

타입이 정하는 것과 호출자가 정하는 것#

type Marshaler interface {
    MarshalJSON() ([]byte, error)
}
type MarshalerTo interface {
    MarshalJSONTo(*jsontext.Encoder) error
}

type Unmarshaler interface {
    UnmarshalJSON([]byte) error
}
type UnmarshalerFrom interface {
    UnmarshalJSONFrom(*jsontext.Decoder) error
}

Marshaler·Unmarshaler 는 v1 그대로입니다. 새로 생긴 MarshalerTo·UnmarshalerFrom 은 타입이 인코더·디코더를 받아 스스로를 스트리밍으로 쓰고 읽게 하며, 인코더·디코더의 Options 접근자로 호출 스택 위에서 내려온 옵션을 읽을 수 있습니다. 객체 멤버 순서를 유지하는 타입은 OrderedObject 예제가 보여 줍니다.

func WithMarshalers(*Marshalers) Options

type Marshalers struct { ... }
func MarshalFunc[T any](fn func(T) ([]byte, error)) *Marshalers
func MarshalToFunc[T any](fn func(*jsontext.Encoder, T) error) *Marshalers

func WithUnmarshalers(*Unmarshalers) Options

type Unmarshalers struct { ... }
func UnmarshalFunc[T any](fn func([]byte, T) error) *Unmarshalers
func UnmarshalFromFunc[T any](fn func(*jsontext.Decoder, T) error) *Unmarshalers

v2 에서는 타입이 아니라 Marshal·Unmarshal 을 부르는 쪽도 임의의 타입에 표현을 지정할 수 있고, 호출자 지정이 타입의 메서드와 기본 표현보다 우선합니다. 남의 패키지 타입의 JSON 표현을 내 호출에서만 바꿀 수 있다는 뜻입니다. 글이 든 예는 모든 proto.Message 를 protojson 으로 보내는 ProtoJSON 예제입니다.

v1 과 달라진 기본 동작과 되돌리는 옵션#

블로그가 꼽은 대표 변경은 여섯 가지입니다. 깨진 UTF-8 에 오류, 중복 이름에 오류, nil 슬라이스·맵은 빈 배열·객체, 필드 매칭은 대소문자 구분, omitempty 는 "인코딩 결과가 null·""·[]·{} 면 생략"으로 재정의, time.Duration 은 기본 표현이 없어 오류. 전체 목록은 v1 패키지 문서의 "Migrating to v2" 절에 있어서 그쪽을 옮깁니다. 옵션 접두사가 없는 것은 json/v2, jsontext. 가 붙은 것은 그 패키지 것입니다.

항목v1v2v1 동작으로 되돌리는 옵션
잘못된 UTF-8U+FFFD 로 바꿔 넣는다오류jsontext.AllowInvalidUTF8
중복 멤버 이름허용오류jsontext.AllowDuplicateNames

표의 마지막 줄은 조심할 만합니다. v1 에서는 조용히 넘어가던 잘못된 struct 태그가 v2 에서는 실행 중 오류가 되므로, 옮기자마자 터지는 쪽은 데이터가 아니라 타입 정의일 수 있습니다. 가이드는 이 옵션으로 덮기보다 태그를 고치라고 권합니다.

열여섯 줄 중에 제 손에 걸릴 것은 두 개였습니다. 맵 순서가 비결정적이 되는 것과 omitempty 의 기준이 바뀌는 것. 앞의 것은 테스트의 골든 파일이 흔들리는 종류라 바로 티가 나고, 뒤의 것은 구조체 값 0 이 전에는 빠졌다가 이제 나가게 되는 종류라 티가 늦게 납니다. 중복 키 거부처럼 "안전해졌다"고 소개되는 변경보다 이런 조용한 쪽이 이전 비용을 정한다고 봅니다.

성능: Unmarshal 이 최대 10배#

글의 요약은 짧습니다. Marshal 은 v1 과 대체로 비슷하고 어떤 경우 조금 빠르고 어떤 경우 조금 느리다. Unmarshal 은 v1 보다 현저히 빠르며 벤치마크에서 최대 10배. 더 큰 이득은 기존 Marshaler·Unmarshaler 구현을 MarshalerTo·UnmarshalerFrom 으로도 구현해 스트리밍으로 처리할 때 나옵니다. 예로 든 것은 Kubernetes 의 한 서비스가 UnmarshalJSON 안에서 OpenAPI 명세를 재귀 파싱하다 성능이 크게 깎였고, UnmarshalJSONFrom 으로 바꾸자 자릿수 단위로 좋아졌다는 kube-openapi#315 입니다. 수치의 출처인 go-json-experiment/jsonbench README 는 v1 을 1 로 두고 데이터셋 여섯 개(CanadaGeometry·CITMCatalog·SyntheaFHIR·TwitterStatus·GolangSource·StringUnicode)로 잰 범위를 적어 두었습니다. 아래는 그중 v2 대 v1 만 뽑은 것입니다. 측정은 Ryzen 9 9950X, Go 1.23.5 시점의 실험 모듈이라 1.27 정식판 수치는 아닙니다.

README 의 결론은 v2 가 대안들과 대체로 같거나 빠르다는 것인데, 구체 타입 Unmarshal 에서는 unsafe 를 쓰는 sonic·go-json 보다 느린 경우가 있다고 적습니다. 중복 이름 검사와 UTF-8 검증 같은 안전 기본값의 값이 거기 들어 있다는 설명입니다. 블로그는 v2 가 v1 보다 느린 경우의 최적화를 계속하고 있으며 Go 1.28 에서 추가 개선을 기대해도 된다고 합니다.

v1 은 v2 위에 있다: 호환과 이전#

이 글에서 가장 쓸모 있다고 본 부분입니다. v1 과 v2 모두 Go 1 호환성 약속의 대상이고 v1 앱은 영원히 지원되며 옮길 필요가 없습니다. 거기서 한 걸음 더 가서, 설계 목표는 v1 과 v2 를 쓰는 패키지끼리 섞여도 돌아가는 것이었습니다. 내 패키지가 v2 로 마샬하는 구조체 안에 남의 패키지가 v1 MarshalJSON 으로 정의한 타입이 있어도 되고, 거꾸로 내가 v1 로 마샬하는데 남의 타입이 v2 의 MarshalJSONTo 를 구현해도 됩니다. 가능한 이유는 v1 이 v2 위에 구현돼 있기 때문입니다. 동작 차이 하나하나가 옵션이고, v1 은 그 호환 옵션 전체를 넘긴 v2 호출입니다. 그 덕에 MarshalJSONTo 메서드나 embed 태그 같은 뒤에 더해진 것이 v1 사용자에게도 자동으로 돌아갑니다.

같은 구조가 호출 하나씩 옮기는 이전을 가능하게 합니다. v2 기본에서 중복 이름만 허용하거나, v1 기본에서 중복 이름만 금지할 수 있습니다. 뒤에 넘긴 옵션이 앞의 것을 덮습니다.

// v2 동작 전부 + 중복 이름은 허용
json.Marshal(..., json.DefaultOptionsV2(), jsontext.AllowDuplicateNames(true))

// v1 동작 전부 + 중복 이름만 금지
json.Marshal(..., jsonv1.DefaultOptionsV1(), jsontext.AllowDuplicateNames(false))

마이그레이션 가이드는 위험 허용도에 따라 세 길을 적습니다.

길맞는 곳순서
한 번에단순한 앱, 깨져도 되는 곳import 를 encoding/json/v2 로 바꾸고 테스트를 돌린 뒤 문제의 원인 옵션만 켠다.
옵션 하나씩복잡하거나 조심스러운 곳모든 호출을 v2 + DefaultOptionsV1() 로 바꾼다(동작 불변). 그 뒤 옵션을 하나씩 떼며 확인한다.
jsonsplit프로덕션 서버github.com/go-json-experiment/jsonsplit 으로 v1·v2 를 둘 다 부르되 v1 결과를 돌려주고(CallBothButReturnV1), AutoDetectOptions·ReportDifference 로 차이를 모니터링한다. 차이가 멎으면 CallBothButReturnV2 또는 OnlyCallV2 로 넘긴 뒤 jsonsplit 을 걷어낸다.

jsonsplit 으로 둘 다 부르면 마샬 비용이 두 배가 되므로 SetMarshalCallRatio 로 일부 호출만 검사할 수 있습니다. 가이드는 출력 차이가 곧 장애는 아니지만 장애가 생길 기회라는 말을 덧붙입니다. 아래 소비자가 null 에 의존하고 있었다면 빈 배열이 곧 사고입니다.

6년이 걸린 사연#

2020년 말, v1 유지보수자 Daniel Martí 가 고칠 수 없는 문제들에 밀려 가상의 v2 가 어떤 모양일지 초안을 적었습니다. 따로, Protocol Buffers 의 Go API 작업을 끝낸 Joe Tsai 는 protojson 이 자체 JSON 구현을 써야 했던 것에 실망해 있었습니다. v1 은 protobuf 명세가 요구하는 더 엄격한 표준을 따를 수도, 스트리밍으로 직렬화할 수도 없었기 때문입니다. 둘이 합쳐 프로토타입을 만들었고 초기 코드는 Go protobuf 모듈의 JSON 직렬화 로직을 다듬은 것이었습니다. 그 뒤 Roger Peppe·Chris Hines·Johan Brandhorst-Satzkorn·Damien Neil·Austin Clements·Michael Pratt 가 설계 검토·코드 검토·회귀 테스트로 합류했고, 초기 회의 녹화와 메모가 공개돼 있습니다.

  • 2023년 말 GopherCon 발표와 공개 토론(golang/go#63397)
  • 2025년 초 정식 제안(#71497)
  • Go 1.25 에서 GOEXPERIMENT=jsonv2 실험으로 채택, 전 사용자 대상 테스트
  • Go 1.27 에서 정식 안정 API

글은 이 작업이 대부분 Google 소속이 아닌 사람들의 손으로 개발되고 추진됐다는 점을 따로 적고, Go 프로젝트가 협업으로 굴러간다는 증거로 삼습니다.

안 옮겨도 된다는 글을 이렇게 길게 쓴 것은, 안 옮기는 쪽이 이득을 공짜로 받기 때문입니다. v1 호출을 한 줄도 안 고쳐도 의존 패키지가 MarshalJSONTo 를 구현하면 그 속도가 내 쪽으로 넘어옵니다. 새 것을 만들면서 옛 것을 그 위에 다시 얹는 수고를 6년 동안 한 사람들이 있었고, 저는 그 수고 덕에 결정을 미룰 수 있게 됐습니다. 결정을 미루게 해 주는 설계를 저는 가장 높게 칩니다. 다음 페이지에서 뵙겠습니다. 아마 내일쯤이요.
