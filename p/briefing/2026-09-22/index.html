02PostgreSQL 캐싱: 기본 동작과 추가 캐시의 선택 기준

PostgreSQL은 데이터 페이지와 실행 계획은 캐싱하지만 쿼리 결과는 저장하지 않습니다. 그래서 캐시 적중률이 99%여도 같은 쿼리를 너무 자주 돌리면 CPU가 포화될 수 있습니다. 캐시를 더 붙이기 전에 디스크 때문에 느린지, 반복 실행 때문에 느린지부터 가려야 합니다.

  • shared_buffers는 직접 운영하는 전용 서버에서 RAM의 25%가 시작점이고, OS 캐시와 중복되므로 40%를 넘겨 봐야 얻는 게 적습니다. effective_cache_size는 메모리 할당이 아니라 플래너용 힌트입니다.
  • 반복 집계는 구체화 뷰, 자주 읽는 결과는 Redis나 프록시 캐시, 변경 스트림 기반으로는 Readyset·PgCache가 있지만 각각 갱신 비용과 최신성 지연이 다릅니다.
  • 쓰기가 많거나 반복 조회가 적으면 캐시는 관리 부담만 늘립니다. pg_stat_statements와 EXPLAIN (ANALYZE, BUFFERS)로 인덱스와 쿼리부터 보는 편이 쌉니다.

05프롬프트는 실재하지 않는다

06Worktrunk - 여러 코딩 에이전트의 Git 작업 공간을 관리하는 CLI

Claude Code나 Codex에 여러 작업을 동시에 맡길 때 에이전트마다 별도 작업 디렉터리를 주려고 Worktrunk를 만들었습니다. git worktree의 생성·이동·삭제를 브랜치 이름만으로 처리하고, wt switch -c -x claude feature-a 한 줄로 브랜치와 작업 공간, 에이전트 실행까지 끝냅니다.

  • wt list와 대화형 선택 화면에서 작업 공간별 변경, 커밋, 원격 상태, diff, PR 댓글까지 미리 볼 수 있습니다.
  • 생성과 병합 전후 훅으로 의존성 설치나 테스트를 자동화하고, wt merge가 커밋 정리·리베이스·병합·작업 공간 삭제를 이어서 처리합니다.
  • 지원 파일시스템에서는 빌드 캐시와 node_modules를 복제해 작업 공간마다 새로 설치하는 부담을 줄이고, 개발 서버 포트도 자동으로 나눠 줍니다.
