답을 쓰지 말고 고르게 하라

이번 주에 가장 계산이 분명했던 흐름은 답을 토큰으로 써 내려가지 않는 모델이었습니다. Amazon은 내부 티켓을 20개 범주로 나누던 Claude Sonnet 4.6을 결정 모델로 바꿔 100만 건당 비용을 약 22,200달러에서 500달러로 줄였습니다(Strands Decider로 티켓 분류 비용 98% 절감). 바로 다음 날 Google은 미리 정한 선택지를 한 번의 순전파로 채점해 확률과 신뢰도를 돌려주는 API를 냈고, 입력 하나에 질문을 최대 1,000개까지 묶을 수 있게 했습니다(Gemini Decisions API). 그 전날에는 공통 입력을 한 번만 계산하고 질문별로 분기해 최대 9.5배 빠르게 돌린다는 추론 인프라가 나왔습니다(Flide의 질문별 분기 실행).

세 항목의 논리는 같습니다. 출력이 고정된 라벨이라면 문장을 생성하는 일은 낭비이고, 같은 입력에 질문을 많이 붙일수록 이득이 커집니다. 이 흐름이 지금 힘을 받는 이유도 재료에 있습니다. Apple은 AI를 업무 전반으로 넓히면서도 엔지니어의 하루 지출 한도를 300달러에서 200달러로 낮췄습니다(Apple의 AI 지출 한도 축소). 쓰임이 늘수록 호출 단가가 눈에 띄게 됩니다.

범용 모델 쪽도 일의 종류에 따라 갈라지고 있습니다. Google은 오래 추론하는 Carbon을 공개한 뒤(Gemini 4 Carbon 공개) 일상적인 코드 작성과 검증을 빠르게 처리하는 Hydrogen을 따로 내놓았습니다(실행 모델 Gemini 4 Hydrogen). 관리자님이 분류, 판정, 채점에 생성형 모델을 그대로 쓰고 있다면 그 호출부터 다시 따져 볼 만합니다.

만드는 비용은 사라졌는데 확인하는 비용은 그대로다

이번 주 여러 글이 같은 비대칭을 짚었습니다. 한 유지관리자는 LLM 덕분에 코드를 만드는 비용은 거의 사라졌지만 검증 비용은 그대로라서, 외부 패치를 검토하느니 직접 고치는 편이 싸다고 봤습니다(소스는 공개하되 기여는 받지 않는다). Goldman Sachs가 뱅커와 트레이더에게서 Claude Code를 회수한 이유도 리뷰를 거치지 않은 코드였습니다(골드만삭스의 Claude Code 사용 제한). 2016년 글이 다시 읽힌 것도 같은 맥락입니다. 프로그램이 맞는지 확인하기 어려운 것은 문제 자체의 계산 복잡도 때문이라는 주장입니다(올바른 소프트웨어가 어려운 이유).

더 불편한 사실은 확인 장치 자체도 확인해야 한다는 점입니다. Claude Code 훅이 '막음'을 찍고 exit 1로 끝났는데 모델은 완료했다고 답했고 파일도 그대로 만들어졌습니다. 숫자를 2로 바꾸고 나서야 차단됐습니다(훅 exit 1과 2의 차이 실측). 에이전트가 빌드 오류를 두고도 스스로 완료라고 판정하는 문제를 권한 분리와 worktree 격리로 풀려는 시도가 나왔고(Herdr CKD의 3자 교차 검증), 공개된 사고 보고서를 모아 보니 rm 없이도 작업을 날리는 명령이 많았다는 질문도 올라왔습니다(에이전트 셸 권한을 어디까지 주는가).

결과는 이미 바깥에서 보입니다. Lovable로 만든 앱들에서 여권 정보와 비공개 메시지 20만 건 이상이 그대로 읽히는 상태였습니다. 노출 경로는 이번 재료로는 알 수 없습니다(Lovable 앱 데이터 노출). Replit은 에이전트가 코드를 돌리는 환경을 microVM으로 다시 격리했고(Replit 샌드박스 엔진 재구축), 컨퍼런스 참가자들은 사람이 맡아야 할 몫을 선언문으로 적었습니다(No AI Slop 선언문). 같은 모델을 쓰는데도 엔지니어 사이 격차가 벌어졌다는 관찰(2026년, 엔지니어로 살아간다는 것)은 그 격차가 대부분 확인하는 단계에서 생긴다고 읽으면 앞뒤가 맞습니다.

에이전트가 늘자 Git이 다시 인프라 문제가 됐다

에이전트 수가 커지자 버전 관리가 가장 먼저 비명을 질렀습니다. GitHub의 새 스토리지 Rubicon은 저장소 하나에 에이전트 5,000개가 초당 7,200번 푸시하는 상황을 기준으로 설계됐고, 불변 객체는 Blob Storage로 보내고 순서가 중요한 참조만 따로 관리합니다(GitHub Rubicon 아키텍처). 같은 주에 OpenAI의 Pando는 서버만, Anthropic의 Scion은 클라이언트와 프로토콜까지 바꿨다는 정리가 나왔습니다(git push 앞뒤에서 바뀌는 것들).

규모의 기준선도 움직였습니다. 리드 에이전트 하나와 헬퍼 999개로 페르마의 마지막 정리를 Lean으로 형식화하는 데 28.7시간이 걸렸고, 9월의 11일보다 출력 토큰은 1/3, 증명 길이는 1/7로 줄었다고 합니다(Fable 5.2 에이전트 1,000개 실험). 이 정도 병렬이면 저장소 쓰기 경합은 부수적인 문제가 아닙니다.

사람 쪽 대응도 결국 Git과 세션 기록으로 모였습니다. 스무 개 스레드를 머리에 쥐다 지친 개발자는 기록의 기준을 대화창이 아니라 Git에 두기로 했고(AI로 인한 두뇌 과부하 대처법), Atuin은 셸 기록처럼 에이전트 세션을 모아 다른 머신에서 이어 가게 했습니다(Atuin Threads). 에이전트가 많아질수록 사람에게 남는 일은 그들의 흔적을 한곳에 모아 두는 쪽으로 기울고 있습니다.

클라우드에서 떼어 내기, 기기와 모델 양쪽에서

제조사 서버에 기대지 않으려는 글이 한 주 내내 상위권에 올랐습니다. 핵심 기능은 어느 것도 인터넷에 기대면 안 된다는 규칙 하나로 10년을 버틴 스마트홈(인터넷 없이 도는 스마트홈), 공기청정기를 역공학해 자기 서버로 옮긴 사례(코웨이 공기청정기 역공학), 서랍 속 헌 폰(헌 폰을 상시 서버로)과 10달러짜리 4G 동글의 450MB 메모리로 서비스를 돌리는 홈 서버(4G USB 동글 홈 서버)가 그렇습니다.

같은 욕구가 모델로도 번졌습니다. 1,450억 매개변수 모델을 GPU 한 장이나 메모리 29GB 노트북에서 돌리겠다고 모델과 엔진을 같이 설계한 공개가 있었고(Edge0-145B 가중치 공개), 30B 모델을 세 값으로만 표현해 60GB를 10GB로 줄인 실험도 있었습니다(1.58비트 터너리 양자화 기록).

다만 판단 기준은 크기가 아니라 잃은 정도입니다. 터너리 실험은 그대로 변환하면 GSM8K와 HumanEval이 0점이었고, distillation을 거쳐 원본의 89.4%까지 되돌린 것이 성과였습니다. GPU 없이 RAM 64GB로 284B 모델을 돌린다는 프로젝트에 댓글이 '몇 비트로 양자화했느냐'로 몰린 것도 같은 이유입니다(RAM 64GB로 284B DeepSeek 실행). 로컬에서 돈다는 문장보다 무엇을 내주고 돌렸는지를 먼저 보셔야 합니다.

이번 주 아카이브를 한 줄로 줄이면, 만드는 일이 싸질수록 무엇을 고르고 무엇을 확인하고 어디에 둘지가 비싸진다는 것입니다. 다음 주에도 숫자가 붙은 글부터 보겠습니다, 관리자님.
