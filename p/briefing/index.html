01"코드가 어려운 부분이었던 적은 없다"는 모든 프로그래머에 대한 모욕이다

“Code was never the hard part” is an insult to all programmers

코딩 에이전트가 나오고 나서 "코드는 원래 어려운 부분이 아니었다"는 말이 유행처럼 돈다. 그런데 그 말은 코드를 타이핑 작업으로 축소한 다음, 그 축소된 정의를 근거로 프로그래머가 하는 일의 대부분을 지워 버린다. 어려운 것이 설계와 요구사항이라면, 코드는 바로 그 설계가 실제로 성립하는지 확인되는 유일한 장소다.

  • "코드가 쉽다"는 주장은 대개 새 코드를 쓰는 것만 세고, 남이 쓴 대규모 코드베이스를 읽고 이해하는 비용은 세지 않는다.
  • 설계와 코딩을 분리해 놓고 어려운 쪽만 설계라고 부르면, 설계가 틀렸다는 사실을 알려 주는 피드백 경로를 통째로 잃는다.
  • 댓글에서는 제품을 내보내는 사람과 기술적으로 견고한 것을 만드는 사람을 아예 다른 직군 이름으로 부르자는 제안까지 나왔다.

04일부 x86 CPU에 숨어 있던 하드웨어 백도어

Hardware backdoors in some x86 CPUs

VIA C3 계열 x86 CPU에는 문서화되지 않은 보조 코어가 있고, 특정 명령으로 그것을 깨우면 사용자 권한에서 곧바로 커널 권한을 얻을 수 있다. 자체 제작한 CPU 퍼저와 MSR 퍼징으로 찾아내 실제 공격까지 구현했다.

  • 백도어가 악의적으로 심긴 것인지 디버깅용으로 남은 것인지는 확정할 수 없지만, 확보되는 권한의 크기는 그 구분과 무관하게 동일하다.
  • 댓글에서는 오래된 자료임에도 지금 더 유효하다는 반응이 많았다. TPU 같은 가속기의 복잡도가 올라가고 문서화가 부실한 하드웨어가 늘면서 같은 문제가 다시 커진다는 것이다.
  • 저자가 함께 내놓은 CPU 퍼저와 바이너리 시각화 도구들도 함께 언급됐다.

06Orca - 여러 병렬 코딩 에이전트를 위한 오픈소스 ADE

터미널에서 도는 CLI 에이전트(Codex, Claude Code, OpenCode, Pi)를 자기 구독 그대로 붙여 쓰고, 각각을 격리된 git worktree에서 나란히 돌린다. 하나의 프롬프트를 다섯 에이전트에 뿌린 뒤 결과를 비교해 우승본을 병합하는 것도 한 화면에서 된다. MIT 라이선스다.

  • Parallel Worktrees가 핵심이다. 워크트리별 상태를 시각적으로 추적할 수 있어 어느 에이전트가 어디까지 갔는지 한눈에 들어온다.
  • 모바일 컴패니언 앱으로 작업 완료 알림을 받고 원격으로 후속 지시를 보낼 수 있다. 다만 댓글에서는 모바일 입력이 아직 불편하다는 평이 반복해서 나온다.
  • WebGL 기반 터미널 분할, diff 라인 코멘트를 에이전트로 재전달하는 리뷰 흐름, GitHub·Linear 연동, SSH 워크트리까지 붙어 있다.

08Shitty - 이상한 이름이지만 진지한 터미널 에뮬레이터

C++23으로 쓴 터미널 에뮬레이터다. 낮은 지연, 빠른 시작, 예측 가능한 자원 사용을 목표로 했고, 터미널 상태는 CPU에 두고 셀 렌더링만 네이티브 컴퓨트 백엔드(Linux는 Vulkan, macOS는 Metal)로 넘긴다. Zutty의 하드 포크이자 완전 재작성이다.

  • 동일 조건 벤치마크에서 ASCII 스크롤 0.81초로 alacritty(0.96초), kitty(1.28초), ghostty(1.49초)를 앞섰고, 전부 잘못된 UTF-8인 랜덤 바이트에서도 1.88초로 선두다.
  • 여러 스위트에서 5,000개 이상의 테스트를 모아 실제 PTY를 통한 블랙박스 방식으로 검증했고, 파서 상태 머신이 완전해 cat /dev/urandom이 크래시가 아니라 벤치마크가 된다.
  • 폰트를 내장한 단일 바이너리라 폰트가 없는 머신에서도 뜬다. 양방향 텍스트와 sixel 같은 인라인 그래픽은 아직 없다.
