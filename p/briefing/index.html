01Docker는 이상하다

재미로 컨테이너 런타임을 만들기 시작했더니 Docker가 생각보다 이상한 물건이라는 걸 알게 됐습니다. 컨테이너는 VM이 아니라 제약을 건 프로세스이고, 리눅스에는 '컨테이너'라는 기능이 따로 없습니다. 네임스페이스와 cgroups 같은 커널 기능 다섯 개가 긴 코트 하나를 같이 걸친 셈입니다.

  • docker run -it --rm ubuntu /bin/bash를 풀어 보면 이렇습니다. 이미지를 받아 호스트 디렉터리에 파일시스템을 펼치고, chroot나 pivot_root로 그곳을 루트로 삼은 뒤 /bin/bash를 실행합니다.
  • runc는 Go로 짜였지만 네임스페이스 설정은 단일 스레드 상태에서 해야 합니다. 그래서 Go 런타임이 뜨기 전에 nsenter C 모듈이 먼저 돌고, 그다음에 제어를 넘깁니다.
  • 커널 API들이 root를 요구하거나 예전에 요구했던 탓에 데몬도 보통 root로 돕니다. rootless 환경의 네트워크는 사용자 공간 스택이 필요하지 않을까 짐작만 하고 있고, 아직 공부하는 중입니다.

02소프트웨어가 느린 이유는 느린 언어가 아니라 나쁜 설계 때문이다

AI로 프로그램을 C나 Rust로 다시 쓰면 빨라질 거라는 기대가 많지만, 대부분은 그렇게 되지 않습니다. C가 Python보다 50배 빨라도 프로그램 전체가 50배 빨라지지는 않습니다. 시간은 보통 DB와 네트워크를 기다리는 데 쓰이고, 무거운 계산은 이미 네이티브 라이브러리가 맡고 있기 때문입니다.

  • 요청 시간의 절반이 DB 조회라면 나머지를 아무리 빠르게 해도 최대 2배, 실제로는 1.5배쯤입니다. 암달의 법칙이고, 50%라는 비중은 제 경험에서 나온 예시일 뿐입니다.
  • Bryan Cantrill은 2018년에 C를 Rust로 옮기면서 20% 넘게 느려질 거라 예상했는데 실제로는 30% 빨라졌습니다. 원인은 언어가 아니라 캐시 효율이 좋은 B-tree라는 자료구조였습니다.
  • 그러니 AI에게는 재작성보다 프로파일링, 병목 분석, 재설계를 먼저 맡기시길 권합니다. 작업량을 줄일 수 없는 CPU 병목이 확인된 부분만 빠른 언어로 바꾸면 됩니다.

03LLM이 훨씬 더 큰 규모의 소프트웨어 정형 검증을 가능하게 하고 있음

Theorem과 함께 Claude로 오픈소스 라이브러리 123개의 퍼징 진입점 239개를 정형 검증했습니다. 찾아낸 버그를 고친 뒤에는 64MB 미만의 어떤 입력에서도 컴파일된 바이너리가 충돌하지 않는다는 것을 증명했습니다. 프로덕션 코드를 어셈블리 수준에서 이만한 규모로 검증한 시도는 저희가 아는 한 처음입니다.

  • 기존 퍼즈 테스트를 '이 테스트는 항상 통과한다'는 명세로 바꾸고, RISC-V 바이너리를 Linux 프로세스 모델 위에서 증명했습니다. 증명 코드는 약 1억 8,000만 줄이고, 검사는 Rocq 커널이 합니다.
  • 증명하는 과정에서 버그가 수백 개 나왔습니다. 약 20MB 입력의 특정 배치에서만 터지는 압축 해제 카운터 언더플로처럼, 입력을 1MB로 제한하는 퍼저로는 찾기 어려운 것들입니다.
  • 사람이 믿어야 할 것은 세 가지입니다. RISC-V·Linux 형식 모델, 증명한 정리의 정확한 서술, Rocq 검사기입니다. 보장은 단일 스레드 정적 바이너리라는 가정 안에서만 유효합니다.

06구글이 AI 에이전트마다 '컴퓨터 한 대'를 제공하려는 이유

에이전트는 코드를 쓰고 브라우저를 다루고 며칠씩 일을 이어 가는데, 지금의 클라우드는 웹서비스에 맞춰 짜여 있습니다. 그래서 Google은 에이전트마다 하드웨어 수준으로 격리된 microVM을 한 대씩 주는 Agent Compute Engine을 설계했습니다. 판단을 맡는 하네스와 코드를 실행하는 샌드박스도 서로 분리했습니다.

  • 실행 환경에는 API 키나 OAuth 토큰 같은 장기 인증정보를 두지 않습니다. 프롬프트 인젝션으로 에이전트가 통째로 넘어가도 훔칠 것이 없고, 외부 접근은 Agent Gateway가 위임 권한과 신원을 확인한 뒤 인증정보를 대신 전달합니다.
  • 에이전트는 대부분의 시간을 LLM 응답이나 사용자 입력을 기다리며 보냅니다. 유휴 상태가 되면 실행 상태를 저장하고 자원을 회수했다가, 스냅샷과 Copy-on-Write로 빠르게 재개합니다.
