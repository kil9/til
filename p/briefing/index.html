02Git 사용자를 위한 Jujutsu(jj) 워크숍

Git 객체 모델부터 짚고, jj 가 그걸 어떻게 다르게 다루는지 손으로 따라가 보는 3시간 반짜리 워크숍입니다. jj 에는 인덱스도 stash 도 없고 working copy 자체가 커밋입니다. 마지막 부에서는 Tangled 와 GitHub 에 jj 로 push 하는 흐름까지 보여 드립니다.

  • change ID 와 commit ID 가 분리되어 있어서, 내용이 바뀌어도 같은 변경을 계속 추적할 수 있습니다.
  • 충돌은 일급 객체입니다. rebase 가 멈추지 않고 충돌 상태를 커밋에 기록해 두었다가 나중에 해결하면 됩니다.
  • jj undo 와 op log 로 저장소 전체 작업 단위를 되돌릴 수 있고, 메가 머지로 여러 작업 브랜치를 동시에 개발할 수 있습니다.

07검증 패턴 도입기 - PR마다 에이전트가 검증한 것과 못 한 것을 기록하게 하기

규칙은 하나입니다. 모든 PR 은 verifications/{PR 번호}.md 에 하네스가 검증한 것과 검증하지 못한 것을 적어야 하고, 이 파일이 없으면 ready 로 바꿀 수 없습니다. 로컬에서 돌릴 수 있던 린트에 실패한 채 CI 로 올라오는 PR 이 너무 많았기 때문입니다.

  • 기록을 강제하면 하네스는 한 일을 보여 주거나 건너뛰었다고 인정하거나 둘 중 하나를 해야 합니다. Chain-of-Thought 처럼 원하는 행동 쪽으로 끌어 주는 장치라고 봅니다.
  • 쌓인 검증 파일에서 빈틈을 찾아 매일 자동으로 이슈와 개선 PR 을 만들고, 그래서 영역마다 매일 아침 4-6개의 PR 이 리뷰를 기다립니다.
  • 팀마다 어긋난 지침은 컨텍스트 독으로 보고 중앙화 쪽을 택했지만, 얼마나 중앙화할지는 아직 확신하지 못합니다.
