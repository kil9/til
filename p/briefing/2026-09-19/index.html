02마틴 파울러: 나는 LLM이 마음에 들지 않는다

LLM이 생산성을 올릴 수 있다는 건 인정합니다. 그래도 직접 대화할 때는 기대나 두려움보다 거부감이 먼저 옵니다. 쓸 만한 답과 지어낸 말을 같은 확신으로 내놓고, 틀렸다고 하면 진심 없는 사과로 넘어가는 태도가 싫습니다.

  • 그렇다고 쓰지 말자는 건 아닙니다. Jessica Kerr 말대로 더 빠르고 철저하니 안 쓰는 게 무책임할 수도 있습니다. 쓸모와 호감은 별개입니다.
  • 에이전트는 의식이 있는 존재가 아니라 회사가 만든 소프트웨어이고, 실리콘밸리 브로그래머 문화의 가치관 속에서 길러집니다.
  • 저는 불쾌하거나 믿을 수 없는 사람과는 일도 같이 하지 않으며 살아왔습니다. LLM은 사람을 흉내 내는 데서 그치지 않고, 평소라면 제가 피할 유형의 사람을 흉내 냅니다.

03OpenSpec - 코딩 에이전트와 구현 전에 명세를 맞추는 개발 도구

OpenSpec은 대화 기록에만 남아 있던 요구사항을 명세와 구현 계획으로 끌어내서, 사람이 검토한 뒤에 에이전트가 코드를 쓰게 합니다. 변경 하나마다 제안서, 명세, 설계, 작업 목록을 한 폴더에 묶어서 무엇을 왜 바꾸는지 코드 옆에 남깁니다.

  • openspec/specs/에는 현재 시스템 동작을, 각 변경에는 추가·수정·삭제분만 적는 delta spec을 둡니다. 기존 코드베이스 전체를 먼저 문서화하지 않아도 됩니다.
  • /opsx:explore → propose → apply → sync → archive 흐름이 기본인데, 순서는 문서 간 의존일 뿐이라 구현 중에 design.md로 되돌아가 고쳐도 됩니다.
  • Claude Code, Codex, Cursor, Copilot 등에서 명령이나 스킬로 쓰고, Markdown 파일이며 MIT 라이선스입니다.

04Bonsai 2 27B, 성능 98.2%를 유지하며 모델 크기를 5.9GB로 압축

Qwen3.8 27B를 바탕으로 가중치를 −1, 0, +1 세 값과 그룹별 FP16 배율로 표현한 Ternary Bonsai 2 27B를 공개합니다. 가중치당 실효 1.76비트, 전체 5.9GB로 원본의 9분의 1이 안 되지만 종합 벤치마크 성능은 98.2%를 유지합니다.

  • 사고 모드 종합 83.9점으로 원본 Qwen3.8 27B(85.4)에 근접했고, 지시 따르기는 원본보다 높습니다. 이전 세대의 유지율 95%에서 98% 이상으로 올라갔습니다.
  • 자체 측정 기준 RTX 5090에서 최대 143토큰/초, M5 Max에서 46.8토큰/초이며 262K 컨텍스트와 이미지 입력을 지원합니다.
  • CUDA와 MLX 전용 저비트 커널로 돌아가고 가중치는 Apache-2.0입니다. GGUF를 쓰려면 PrismML의 llama.cpp 포크가 필요하다는 반응이 있었습니다.

05HarnessTax: 코딩 에이전트에서 하네스는 얼마나 중요할까?

모델 7개를 Claude Code, Codex CLI, Pi에 각각 물려 21개 구성을 비교했습니다. 같은 모델이면 하네스가 달라도 성공률은 비슷했지만 토큰 비용은 최대 5배 차이가 났습니다. 비교해 보지 않으면 드러나지 않는 이 차액을 하네스 세금(Harness Tax)이라고 부릅니다.

  • read, write, edit, bash 네 도구뿐인 Pi도 두 벤치마크에서 파레토 경계에 올랐습니다. SWE-bench Lite에서 Fable 5는 Claude Code 97.8%, Pi 96.7%였고, 시도당 비용은 1.33달러 대 0.67달러였습니다.
  • Claude Code의 첫 호출 초기 문맥은 7개 모델 모두에서 Pi의 10배 이상이었습니다. 다만 총비용에는 캐싱, 출력량, 이후 호출도 영향을 줍니다.
  • Anthropic과 OpenAI 모델 12개 비교 중 9개에서 다른 공급사의 하네스가 가장 높은 성공률을 냈습니다. 벤치마크별 30개 작업이라 여러 세션이 이어지는 실제 개발에 그대로 적용된다는 뜻은 아닙니다.

06백업은 단순하지 않다

백업은 파일을 다른 곳에 복사하면 끝이라고 생각했습니다. 그런데 실수와 랜섬웨어에 대비하려면 현재 상태의 복제가 아니라 과거 상태를 보존해야 했고, 그때부터 복잡성이 계속 쌓였습니다. 반나절이면 될 줄 알았던 일이었습니다.

  • RPO를 정하면 스냅샷이 쌓이고, GFS 순환과 하드 링크 중복 제거, 증분 백업을 차례로 고민하게 됩니다. rsync와 cron으로 여기까지는 만들 수 있습니다.
  • 홈랩에 적용하면 root 소유 Docker 볼륨 권한과, 그대로 복사한 DB 파일의 복원 가능성이 문제가 됩니다. 덤프를 따로 떠야 합니다.
  • 3-2-1을 위해 S3에 올리면 메타데이터가 사라지고 작은 파일 업로드 비용이 커집니다. tar로 묶으면 증분 방식이 무너지니 결국 Borg나 Restic을 쓰고, 복원까지 실제로 테스트해야 합니다.
