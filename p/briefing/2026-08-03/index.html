  • 진짜 즉시 모드 API라 위젯 상태를 따로 들고 있거나 데이터와 동기화할 필요가 없고, 네이티브 바이너리는 보통 10MB 정도입니다.

03Mac GPU(MPS) 한 줄로 3.5배, Local LLM 파이프라인을 8분에서 4분으로

로컬 LLM 기반 자동 영상 편집 파이프라인을 8분에서 4분으로 줄인 기록입니다. 가장 큰 배수는 멀티스레딩이 아니라 놀고 있던 GPU를 깨운 한 줄 수정에서 나왔습니다. 스레드를 늘리기 전에 자원 지도부터 그리라는 이야기입니다.

  • Ollama 서버는 요청을 직렬 처리하는 공유 자원이라 클라이언트 스레드를 늘려도 서버 앞에 줄만 섭니다. 이득은 전부 Ollama 작업과 비-Ollama 작업을 겹치는 데서 나왔습니다.
  • 검출 모델이 내내 CPU로 돌고 있었고 MPS를 명시하자 157.9초에서 45.4초로 3.5배, 프레임마다 랜덤 시크하던 모션 곡선을 순차 읽기로 바꾸자 약 6배 — 둘 다 병렬화가 아닌 직렬 최적화입니다.
  • 측정 자체가 함정이었습니다. 같은 입력을 세 번 돌리니 28.1 / 22.9 / 14.3초가 나와 Ollama 분산이 구간을 지배했고, 그래서 결정론 구간만 A/B로 숫자를 재고 LLM이 섞인 구간은 출력 동일성과 구조적 산수로만 판단했습니다.
  • 합격 기준은 속도가 아니라 결과 동일성입니다. CPU에서 GPU로 바꾼 뒤 골든셋 5영상의 박스 수, 트랙 수, miss/IDF1 이 소수 4자리까지 같았습니다.

04RSS보다 Atom이 실질적으로 더 나은 이유

RSS는 서로 호환되지 않는 9가지 규격으로 파편화되어 있습니다. RSS 2.0의 description 태그는 내용을 어떻게 해석할지가 모호해서 관습적으로 content:encoded 를 하나 더 붙여야 하고, 제목과 본문이 텍스트인지 HTML인지 구분하는 인코딩 의미론이 아예 정의되어 있지 않습니다.

  • Atom(RFC 4287)은 제목의 type 속성으로 text, html, xhtml 을 명확히 구분합니다. 같은 문제를 규격 차원에서 처리한 셈입니다.
  • 다만 팟캐스트 생태계에서는 애플이 RSS만 지원하고 2023년에 Atom 지원마저 걷어내면서 Atom 이 사실상 배제됐습니다.
  • 웹 피드 기술 자체로 보면 Atom 이 체계적이지만, 어느 쪽을 내보낼지는 소비자가 누구냐에 달려 있습니다.

06Ask GN: MCP 도구를 여러 개 붙여 에이전트를 운영하시는 분들 중 중복 실행 겪어보신분 계실까요?

공개 벤치마크 트레이스에서 에이전트의 중복 실행을 측정했습니다. 6,780개 트레이스에서 같은 도구를 같은 인자로 두 번 호출하고 결과까지 같은 경우가 8,042건, 작업 완료 선언 반복 같은 걸 빼면 4,249건이었습니다. 상태를 바꾸는 도구의 중복 3,432건 중 159건은 응답 엔티티 ID 비교로 실제 두 개가 생성된 게 확인됐습니다.

  • 같은 제목 문서가 두 개, 같은 스프레드시트가 네 개 만들어진 식인데 대부분 에러가 나지 않았습니다. 두 번 다 200이고 로그도 깨끗해서 사후에 로그만 봐서는 보이지 않습니다.
  • 도구 수가 원인이라는 단순한 관계는 못 봤습니다. 태스크에 붙은 서버 수로 나누니 4-5개일 때 약 2.5%로 가장 높고 그 이상에서는 오히려 낮아지는 비단조 패턴이었습니다.
  • 판정 불가 3,197건 중 2,011건이 응답에 엔티티 ID가 없어서였고, ID를 한 번도 안 주는 도구가 24종이었습니다. "두 번 호출됐다"와 "두 개가 생겼다"를 가르는 지점이 여기입니다.
  • 이 숫자는 전부 벤치마크 트레이스이지 실제 운영이 아닙니다. 공개 데이터셋 여덟 개 중 이 현상을 관측할 수 있는 게 하나뿐이었습니다.
