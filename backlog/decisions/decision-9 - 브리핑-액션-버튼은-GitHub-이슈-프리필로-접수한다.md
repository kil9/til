## Context

브리핑 페이지(`p/briefing/`)의 '이 건으로 TIL 만들기' 버튼은 til-inbox 에 접수 이슈를
만들어야 한다. 그런데 브리핑은 공개 경로에 있고, 이슈 생성에는 쓰기 권한이 필요하다.
task-82 는 두 안을 놓고 있었다.

- (a) 브리핑을 비밀 슬러그 경로에 두고 페이지에 PAT 를 심는다
- (b) 공개 브리핑에서는 버튼을 감추고 관리자용 사본에서만 노출한다

둘 다 "토큰이 어딘가 정적 파일에 박힌다"는 문제를 옮기기만 한다. 비밀 슬러그는 URL 이
새는 순간 토큰이 새고, 관리자 사본은 같은 페이지를 두 벌 유지해야 한다.

## Decision

til-inbox 의 이슈 작성 화면을 쿼리스트링으로 미리 채워 새 탭으로 연다.

```
https://github.com/kil9/til-inbox/issues/new?labels=pending&title=…&body=…
```

두 번째 클릭에서 이 URL 을 열고, 관리자는 열린 화면에서 등록만 누른다.
본문 규약은 til-inbox 워처가 이미 쓰는 `SOURCE:` / `REQUEST:` 형식 그대로이고,
`KIND:` 를 비워 두면 기본 경로(submit — 원문을 읽고 til 페이지까지 생성)로 간다.

## Consequences

- 페이지 어디에도 토큰이 없다. 정적 파일 원칙을 그대로 지킨다.
- til-inbox 가 비공개 저장소라는 점이 인증을 대신한다. 관리자가 아니면 그 URL 은
  404 다. 게다가 워처는 `pending` 라벨이 붙은 이슈만 집는데, 라벨은 쓰기 권한이
  있어야 붙으므로 권한 없는 사람이 만든 이슈는 파이프라인을 타지 않는다.
- 대가는 클릭 한 번이다. 버튼 두 번 + GitHub 에서 등록 한 번.
- 인프라를 새로 세우지 않는다. Cloudflare Tunnel + Access(task-73·76)로 nuc14 에
  접수 엔드포인트를 노출하는 안이 그 클릭을 없애 주지만, 서비스·CORS·Access 정책·
  서버측 토큰을 새로 관리해야 한다. 클릭 하나를 줄이자고 치를 값은 아니다.
  접수 빈도가 높아지면 그때 갈아 끼운다 — 두 번째 클릭의 `window.open` 을 `fetch` 로
  바꾸면 되고 본문 규약은 그대로다.
- 새 탭이 팝업 차단에 걸리는 경우를 대비해 요청 본문을 클립보드에도 복사해 둔다.
