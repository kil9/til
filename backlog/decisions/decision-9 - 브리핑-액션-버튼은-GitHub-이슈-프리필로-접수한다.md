## Context

브리핑 페이지(`p/briefing/`)의 '이 건으로 TIL 만들기' 버튼은 til-inbox 에 접수 이슈를
만들어야 한다. 그런데 브리핑은 공개 경로에 있고, 이슈 생성에는 쓰기 권한이 필요하다.
task-82 는 두 안을 놓고 있었다.

- (a) 브리핑을 비밀 슬러그 경로에 두고 페이지에 PAT 를 심는다
- (b) 공개 브리핑에서는 버튼을 감추고 관리자용 사본에서만 노출한다

둘 다 "토큰이 어딘가 정적 파일에 박힌다"는 문제를 옮기기만 한다. 비밀 슬러그는 URL 이
새는 순간 토큰이 새고, 관리자 사본은 같은 페이지를 두 벌 유지해야 한다.

## Decision

**관리자 제출 페이지(`p/submit-…/`)가 이미 쓰던 배관을 그대로 쓴다.** 그 페이지는
til-inbox 전용 fine-grained PAT 를 브라우저 `localStorage['til-inbox-pat']` 에 한 번
등록해 두고 `api.github.com` 으로 직접 이슈를 만든다. 브리핑도 같은 오리진
(`til.kil9.dev`)이라 그 토큰을 그대로 읽는다. 두 번째 클릭에서 POST 가 나가고,
페이지 안에서 "접수했습니다 (#N)" 로 끝난다. 탭도 로그인도 없다.

토큰이 없는 브라우저(또는 401/403)에서만 이슈 작성 화면을 미리 채워 새 탭으로 여는
쪽으로 폴백하고, 그 문구에서 제출 페이지로 안내해 한 번 등록하게 한다.

본문 규약은 til-inbox 워처가 이미 쓰는 `SOURCE:` / `REQUEST:` 형식 그대로이고,
`KIND:` 를 비워 두면 기본 경로(submit — 원문을 읽고 til 페이지까지 생성)로 간다.
선별 피드백(task-90)은 같은 함수에 `feedback` 라벨만 달리 준다.

### 처음에는 프리필만 두었다가 바꾼 이유

첫 구현은 폴백 쪽만 있었다. 실제로 폰에서 눌러 보니 GitHub 에 로그인돼 있지 않아
404 가 떴다 — 비공개 저장소라 미로그인 사용자에게는 존재 자체가 없다. "권한 없는
사람은 어차피 못 연다" 는 성질이 보안으로는 맞지만, 정작 관리자 본인이 매번 로그인
상태를 신경 써야 하는 물건이 됐다. 접수창구가 이미 그 문제를 푼 방식이 있었는데
브리핑만 다른 길을 간 것이 잘못이었다.

## Consequences

- **페이지 파일 어디에도 토큰이 없다.** 토큰은 관리자 브라우저에만 있고, 정적 파일
  원칙을 그대로 지킨다. 공개 URL 을 남이 열어도 그 브라우저에는 토큰이 없으니
  버튼은 폴백(작성 화면)까지만 가고, 비공개 저장소라 거기서 멈춘다.
- 토큰은 오리진 단위로 공유된다 — `til.kil9.dev` 의 어느 페이지든 읽을 수 있다.
  이 사이트는 내가 발행하는 정적 파일만 서빙하므로 새로 생기는 위험은 없지만,
  외부 스크립트를 한 줄이라도 들이면 그때는 이 전제가 깨진다(지금 외부 리소스는
  Cloudflare beacon 하나뿐이고, 그 정책은 AGENTS.md 에 이미 박혀 있다).
- 토큰 만료·회수는 폴백으로 자연히 처리된다. 401/403 이면 작성 화면이 열리고,
  제출 페이지에서 새 토큰을 등록하면 다시 즉시 접수로 돌아온다.
- 인프라를 새로 세우지 않는다. Cloudflare Tunnel + Access(task-73·76)로 nuc14 에
  접수 엔드포인트를 노출하는 안은 토큰 관리까지 서버로 옮겨 주지만, 서비스·CORS·
  Access 정책을 새로 떠안는다. localStorage 방식이 이미 돌고 있는데 치를 값은 아니다.
- 폴백 경로에서는 새 탭이 팝업 차단에 걸릴 수 있어 요청 본문을 클립보드에도 복사해 둔다.
