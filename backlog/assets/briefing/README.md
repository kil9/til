# 리브의 아침 브리핑 — 페이지 템플릿과 노출 정책 (task-81)

파일럿(`drafts/daily-report-pilot.html`, 비커밋 v5)을 정리한 결과물이다. 발행 잡(task-85)이
이 템플릿에 값을 채워 페이지를 만든다.

## 파일

| 파일 | 쓰임 |
| --- | --- |
| `template.html` | 페이지 셸(head·CSS·머리말·footer·액션 JS) |
| `item.html` | 선별 항목 하나(좌 본문 + 우 메타·액션) |
| `item-rest.html` | 하단 '훑고 넘긴 것' 그리드 한 칸 |
| `recap.html` | 주간 리캡 페이지 한 장(§주간 리캡) |
| `archive.html` | 지난 회차 목록(`p/briefing/archive/`) |

치환은 `{{NAME}}` 토큰이다. 값은 HTML escape 한 뒤 넣는다(제목·요약에 `&`·`<` 가 섞여 온다).
`button` 의 `data-*` 속성에 들어가는 값은 큰따옴표 escape 까지 확인한다.

### `template.html` 토큰

| 토큰 | 값 |
| --- | --- |
| `{{DATE}}` | `YYYY-MM-DD` (canonical·OG·요청 본문 SOURCE 에 함께 쓰인다) |
| `{{DATE_KO}}` | `2026-07-26 (일)` |
| `{{DESCRIPTION}}` | 한 줄 설명(meta·OG 공용) |
| `{{FAVICON_B64}}` | 리브 원형 파비콘 base64 (루트 `index.html` 의 것을 그대로) |
| `{{ROOT_REL}}` | 사이트 루트 상대경로. `p/briefing/` 은 `../../`, `p/briefing/<날짜>/` 는 `../../../` |
| `{{ARCHIVE_REL}}` | 아카이브 상대경로(task-87). 그전까지는 `{{ROOT_REL}}p/briefing/` |
| `{{SCANNED}}` / `{{PICKED}}` | 훑은 건수 / 선별 건수 |
| `{{INTRO}}` | 리브 머리말. `<p>` 여러 개, 첫 문단에 `.sticker-hero` 스티커 하나 |
| `{{PICK_ANCHOR}}` / `{{PICK_TITLE}}` / `{{PICK_LINE}}` | 강추 1건의 앵커(`i05` 등) · 그 글 제목(앵커 링크의 글자) · 왜 권하는지 한 줄 |
| `{{TOC_ITEMS}}` | `<li><a href="#i01">…</a></li>` 목록. 순서는 본문과 같다 |
| `{{DAYNAV}}` | 이전/다음 회차 이동 내비(task-92). `<!-- DAYNAV:START -->`\~`END` 마커 안에 들어간다 |
| `{{ITEMS}}` | `item.html` 을 이어 붙인 것 |
| `{{REST_ITEMS}}` | `item-rest.html` 을 이어 붙인 것 |

### `item.html` 토큰

`{{ANCHOR}}`(`i01`…), `{{RANK}}`(`01`…), `{{URL}}`(GeekNews 토픽 링크), `{{TITLE}}`,
`{{LEDE}}`, `{{BULLETS}}`(`<li>` 2-3개), `{{DOMAIN}}`(원문 도메인),
`{{INTEREST}}`(`관심사 최상`/`상`/`중`/`밖` 등), `{{PERCENTILE}}`(추천 백분위 상위 N%),
`{{ACTION_TOPIC}}`·`{{ACTION_URL}}`·`{{ACTION_ANGLE}}`(til 요청 본문 재료).

`{{TIEBOX}}`·`{{LIV}}`·`{{BADGE}}` 는 있을 때만 채우고 없으면 빈 문자열이다. `{{BADGE}}` 는
앞의 구분점(` · `)까지 함께 들고 있으므로 템플릿에서 따로 붙이지 않는다.

```html
<div class="tiebox"><span class="lbl">til 연관</span><a href="{{ROOT_REL}}2026/<slug>/">글 제목</a> 이 …</div>
<div class="liv"><img src="data:image/webp;base64,…" alt="리브" width="72" height="72"><p>한마디</p></div>
```

## 주간 리캡 (task-91, 형식은 task-117)

일간 회차가 그날 안에서만 본다면, 리캡은 며칠에 걸쳐 이어지는 것을 본다.

- **경로는 `p/briefing/recap/<YYYY-MM-DD>/`** 다. 날짜는 발행일(일요일)이고 재료 구간이 아니다.
  `p/briefing/weekly/` 같은 새 경로를 만들지 않는다 — 이미 나간 URL 이 있고 바꿔서 얻을 것이 없다.
- **발행은 일요일 09:20**(`recap.sh` cron). AIwitness 위클리는 화요일이지만 여기는 데일리(매일 09:00)
  리듬에 붙여 그 주가 닫히는 자리에 둔다.
- **재료는 그 주 `state/briefing-<날짜>.json` 뿐이다.** 원문을 다시 수집하지 않는다. 회차가
  `MIN_BRIEFINGS`(3)회 미만인 주는 관통할 흐름이 없다고 보고 리캡을 만들지 않는다.
- **노출은 데일리와 같다.** 갤러리 카드·README 표·`p/archive/` 에 넣지 않고 `noindex, follow` 로
  내보낸다. 진입은 `p/briefing/archive/` 상단의 '주간 리캡' 블록이다. 그 목록은 회차 페이지의
  `<title>… · 주간 리캡</title>` 을 정규식으로 읽으므로 **제목 형식을 바꾸면 목록이 조용히
  날짜 폴백으로 무너진다**(`render.py` 의 `render_archive()`).

### 회차 구성

| 구역 | 만드는 주체 | 토큰 |
| --- | --- | --- |
| 헤드라인 | 모델 | `{{TITLE}}` + `{{DESCRIPTION}}`(`.dek` 로 제목 아래 한 줄) |
| 타임라인 | 코드 | `{{TIMELINE}}` |
| 이야기 | 모델 | `{{BODY}}` |
| 마무리 | 모델 | `{{CLOSING}}`(리브 코멘트 자리) |

- **헤드라인에 새 필드를 만들지 않았다.** 기존 `title`·`description` 이 이미 그 역할이라
  headline 필드를 따로 파면 모델이 둘을 어정쩡하게 나눠 쓴다. 프롬프트가 둘이 같은 말을
  하지 않도록 요구하고, 템플릿이 description 을 본문에도 세운다.
- **타임라인은 모델을 거치지 않는다.** 각 회차의 `sidebar` 한 줄을 요일 행으로 그대로 옮긴다.
  모델에게 '월요일에 무슨 일' 을 시키면 두 가지가 깨진다 — collect 의 backfill 정책 때문에 같은
  항목이 여러 회차에 반복 등장해 "화요일에도 X, 수요일에도 X" 가 되고, 이미 있는 정보를
  지어낼 수 있는 형태로 두 번 싣게 된다. `sidebar` 는 원래 그 회차가 무엇으로 채워졌는지를
  말하도록 쓰인 문장이라 그대로가 가장 정확하다.
- **이야기는 `MIN_STORIES`(2)편 이상**이고 각 편은 소제목 + 본문 2-4문단이다. 미달이면 경고만
  찍고 발행은 한다 — 리캡이 안 나가는 것보다 짧게 나가는 편이 낫다.
- **근거 링크는 대조표를 통과한 것만 산다.** 모델은 `[[2026-08-04#i03|링크 글자]]` 형식으로만
  쓰고, `link_refs()` 가 그 주 회차의 실제 `(날짜, 앵커)` 와 대조해 통과분만 `<a>` 로 세운다.
  없는 조합은 링크를 벗기고 글자만 남긴 뒤 stderr 로 알린다. 모델이 링크를 지어내도 죽은 링크가
  페이지에 나가지 않는다.
- em 대시(`—`)를 프롬프트에서 금지한다. 공개 페이지라 저장소 규약의 적용 대상이다.

### 발행 독립성

리캡과 데일리는 **전용 클론을 따로 쓴다**(`repo-recap/` 와 `repo/`). 예전에는 한 클론을 공유했는데
둘 다 `reset --hard` 를 치므로, 일요일 데일리가 push 재시도로 09:20 을 넘기면 리캡이 진행 중인
작업을 밟았다. 락 파일이 달라(`.lock` / `.lock-recap`) 서로를 막아 주지도 못했다. 공용 락으로 묶는
해법은 한쪽이 다른 쪽의 발행을 통째로 건너뛰게 만들어 더 나쁘다. 클론을 나누면 공유 상태가
없어져 어느 쪽이 죽든 다른 쪽은 그대로 나간다. 값은 디스크 76MB 다.

리캡 발행분은 갤러리 카드가 없으므로 `site-feed.py`·`search-index.py`·`archive-thumbs.py` 의
대상이 아니다. 데일리 회차와 같다.

## 반응 온도 배지 (task-118)

항목의 GeekNews 댓글 반응이 유별난 회차에만 `.foot` 줄 끝에 작은 배지를 붙인다.

- **후보를 고르는 것은 코드, 종류를 정하는 것만 모델이다.** `compose.py` 의 `heat_candidates()` 가
  절대 하한 `HEAT_FLOOR`(댓글 10개) 를 넘으면서 그 회차 댓글수 상위 `HEAT_TOP_N`(2건) 안에 드는
  항목만 후보로 넘긴다. 판정을 통째로 모델에 맡기면 회차마다 기준이 흔들리고 "왜 붙었나" 에
  답할 수 없다. 지금은 임계가 코드에 있어 언제나 답이 있다.
- **하한이 상대 순위와 AND 로 걸리는 이유**는 GeekNews 댓글수의 절대 규모다. 회차 최대가 한 자리인
  날이 흔해서(7회차 실측 중 5회차) 상대 순위만 쓰면 댓글 3개짜리에 배지가 붙는다.
- **종류는 둘**이다(`HEAT_KINDS`). `논쟁` = 찬반·해석이 실제로 갈린다. `화제` = 반응은 몰렸지만
  논조는 한쪽이다. 후보에 올라도 어느 쪽도 아니면 모델이 빈 문자열을 고르고 배지는 안 붙는다.
  `heat_value()` 가 후보 밖·모르는 종류를 무조건 떼므로 모델이 임계를 넘어 붙일 수 없다.
- **회차당 0-2개이고 0개가 정상이다.** 스티커·삽화와 같은 원칙 — 전 항목에 붙으면 장식이 된다.
  논조 재료는 `detail()` 이 이미 긁어 오는 선별분 댓글 본문 5개라 추가 수집이 없다.
- 배지 표시는 면·테두리·새 색 없이 그 줄에서 유일한 굵은 글자다(`.heat`). 액센트 블루는
  상호작용 전용이라 배지에 쓰지 않는다(`DESIGN.md` 의 One Blue Rule).

## 레이아웃 원칙 (파일럿 평가에서 확정)

- 폭은 1160px 2칼럼. til 본문 페이지(720px)보다 넓다. 900px 이하에서 1칼럼으로 접힌다.
- 위에서 아래로 한 번만 읽힌다. 항목마다 좌(본문) + 우(til 연관·리브 한마디·액션)로 완결하고,
  되돌아가서 읽어야 하는 요소를 만들지 않는다.
- 최상단 우측은 오늘의 개요(강추 1건 + 전체 미니 목차, 본문 앵커).
- 선별 제외분은 접지 않고 맨 아래 3열 그리드에 한 줄 요약으로 전부 노출한다.
- til 정합성은 고정 섹션이 아니라 `.tiebox` 하나로 녹인다. 연관이 약하면 생략한다.
- 항목 요약은 '~라는 글이다' 식 3인칭 설명이 아니라 저자가 직접 말하는 어투로 쓴다.
- **항목을 가리킬 때는 번호가 아니라 제목**이다(task-103). 강추 한 줄·머리말·리브 한마디 모두
  「제목」 을 쓰고 그 제목이 앵커 링크가 된다. 본문 `h3` 의 `01`·`02` rank 뱃지만 번호로 남는다 —
  그건 위치 표시라 참조가 아니다. 규칙은 잡의 compose 프롬프트에 있고, 렌더가 `<a href="#i01">01</a>`
  같은 번호 링크를 제목으로 되돌리고 뒤따르는 조사까지 맞춘다(규칙 이전 회차를 다시 렌더해도 고쳐진다).
- 매일 같은 정보(선정 기준·관심사 프로필·수집 범위)는 싣지 않는다. 상설 소개
  페이지(`p/liv-briefing/`, task-84)로 빼고 footer 한 줄로 링크한다.
- 임베드 자산은 hero 스티커 1개 + 아바타 4개까지(약 29KB). 페이지 전체는 100KB 안팎이다.
  실측해 보니 용량을 정하는 것은 자산이 아니라 본문이라, 자산만 줄여서는 못 내려가고
  내리려면 실을 항목 수를 줄여야 한다.
- `render.py` 의 경고 상한(`MAX_BYTES`)은 500KB 다(task-95). 구 상한 100KB 는 실측치와 붙어
  있어 매 회차 경고가 떴고, 매일 뜨는 경고는 곧 안 보게 된다. 이 값은 용량 목표가 아니라
  이상 감지선이다 — 페이지가 이만큼 커졌다면 렌더가 잘못된 것이다.

## 경로·노출 정책

- `p/briefing/` 이 항상 최신 1건, `p/briefing/<YYYY-MM-DD>/` 로 과거분이 누적된다.
  최신판과 날짜판은 같은 내용이고 상대경로 깊이만 다르다(`{{ROOT_REL}}`, 내비는 `{{DAYNAV}}`).
- 회차 사이 이동은 페이지 하단의 하루 단위 내비다(task-92). 발행 시점에 정적으로 박으며,
  새 회차가 나오면 `repatch_daynav()` 가 직전 회차 페이지의 마커 구간만 갈아끼워 '다음'
  링크를 채운다. 그래서 발행 커밋에는 오늘 것 외에 어제 페이지 1개가 함께 들어간다
  (`run.sh` 가 `p/briefing` 을 통째로 add 하는 이유).
- 루트 갤러리 카드·README 표·`p/archive/` 에는 넣지 않는다. 매일 1건이 카드로 쏟아지면
  til 본문 글이 묻힌다. 진입은 루트 사이드바의 '오늘의 브리핑' 링크 한 줄과
  `p/briefing/archive/`(task-87) 두 곳이다. 사이드바에서 그 블록은 '리브의 코멘트'
  아래(월별 목차 위)에 둔다 — 사이드바 위쪽은 소개·코멘트 자리다(task-92).
- 검색엔진에는 `noindex, follow` 로 내보낸다. 브리핑이 til 본문 글보다 많이 잡히면
  사이트의 얼굴이 바뀐다. 링크는 따라가게 두어 원문·til 글로 가는 경로는 살린다.
- 날짜판은 무기한 누적한다. 페이지 100KB × 365 = 연 37MB 수준으로, Pages 한도(1GB)에는
  한참 못 미친다. 저장소 클론이 무거워진다고 느껴지면 그때 보존 기간을 다시 본다.
- `404.html` 리다이렉트 맵에는 등록하지 않는다. 구 평면 URL 시절에 없던 경로다.

## 읽음/안읽음 (task-93)

독자가 사실상 관리자 한 명이라 서버 상태·인증 없이 브라우저 `localStorage` 에만 남긴다.
크롤러는 JS 를 돌리지도 저장하지도 않으므로 이 기록에 섞이지 않는다.

- 키는 `liv-briefing-read`, 값은 방문한 회차 날짜의 JSON 배열. 회차 페이지가 열리는 즉시 기록한다.
- 표시는 두 곳이다. 루트 사이드바 '오늘의 브리핑' 배지(`.briefing-new`, 최신 회차를 안 읽었을 때만)와
  `p/briefing/archive/` 목록의 행 구분(`.row.read` 흐리게 / `.row.unread` 점).
- 사이드바는 최신 회차 날짜를 `p/briefing/latest.json`(render.py 가 발행 때 쓴다)에서 읽는다.
  루트 `index.html` 에 날짜를 박지 않는 이유는 그 파일을 AI 요약 잡이 매일 따로 고쳐 쓰기 때문이다.
- 한계: 브라우저마다 따로 논다(폰에서 읽은 것이 데스크톱에 안 보인다). 저장소가 막힌 브라우저에서는
  표시만 빠지고 레이아웃은 그대로다 — 관련 JS 는 전부 `try`/`catch` 안에 있다.

## `p/briefing/latest.json` (task-93, task-104)

루트 사이드바가 브리핑에 대해 아는 전부다. `render.py` 의 `render_archive()` 가 발행 때마다 쓴다.

```json
{"latest": "2026-07-26", "count": 1, "line": "오늘 회차를 한 문장으로"}
```

- `latest`·`count` 는 발행된 날짜 디렉터리에서 나온다(디렉터리가 진실원본).
- `line` 은 사이드바 '오늘의 브리핑' 아래 한 줄이다. compose 가 `sidebar` 로 만들고(회차 전체를
  대표하는 40자 안팎 한 문장, 강추 1건이 아니다) 렌더가 그대로 옮긴다. 과거 회차를 다시 렌더할
  때는 기존 값을 유지한다 — 최신 회차의 한 줄을 옛 회차 내용으로 덮지 않기 위함이다.
- 루트 `index.html` 의 `.briefing-line` 에 박힌 상설 안내문은 폴백이다. fetch 가 실패하거나
  `line` 이 비면 그 문구가 그대로 보인다. 배지와 한 줄이 같은 fetch 하나를 쓴다.
- 아카이브 목록 위에는 안 읽은 회차 요약 한 줄(`.unread-line`)이 있다(task-96). 건수와 가장
  오래된 안 읽은 회차 링크이며, 전부 읽었거나 저장소를 못 읽으면 `hidden` 인 채로 남는다.
  목록이 최신 순이라 '가장 오래된 안 읽은 것' 은 미독 배열의 마지막 원소다.
