## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
결론: 용량 최적화는 하지 않는다. 사용자 판단 — 무제한 요금제·기가 인터넷 환경이고 외부 유입이 적으며, 요즘 웹에서 1MB 대 페이지는 여유다. 단일 파일 원칙(AGENTS §2-1)은 그대로 두고 base64 인라인도 유지한다. 대형 삽화 사이드카 분리·lazy 로딩·아바타 공용화는 전부 범위 밖(하지 않기로 결정).

남기는 것은 사고 감지용 느슨한 상한 하나다. 목적은 용량 절약이 아니라 '실수로 터진 페이지' 를 발행 전에 알아차리는 것이다 — WebP q75 압축을 건너뛴 원본 PNG 를 그대로 임베드했거나, 같은 이미지를 루프로 여러 번 박았거나, 삽화를 1440px 이 아닌 원해상도로 넣은 경우. 이런 것은 수 MB 에서 수십 MB 로 튄다.

- 경고 임계 5MB. 현재 최대가 1.27MB(upcoming-games-2026h2)이니 정상 발행은 절대 안 걸리고, 압축 사고는 대체로 넘긴다.
- 경고만 하고 발행을 막지 않는다. 의도적으로 큰 페이지를 쓸 수 있어야 한다.
- 브리핑의 500KB 상한(TASK-95)과는 무관하다. 그쪽은 매일 자동 발행이라 성격이 다르다.
- DRAFT-7(발행 전 자동 점검)에 검사 항목으로 흡수해도 된다. 단독으로 스크립트를 만들 가치는 없다.
